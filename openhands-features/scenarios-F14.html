F14 Secrets

12 behaviors · 16 scripts & contracts · Maintained source

Entry points & prerequisites

What this family covers

Secrets are named values the agent can use during conversations. A user lists, adds, edits and deletes them under Settings → Secrets; saved values are never shown again, and every new conversation receives them as environment variables.

How a user gets here

  • Sidebar settings gear (backend-selector-settings-link), then Secrets in the settings navigation (sidebar-settings-/settings/secrets).
  • Direct URL /settings/secrets.
  • Command menu (Control+k or Meta+k, or command-menu-trigger in the sidebar): search "Secrets", choose Secrets settings.
  • The agent itself, in a conversation: its request_secret client tool opens the request dialog (testid=secret-request-modal) on /conversations/<id> (F14.agent-request).

Given

Preconditions:

  • Baseline state (launched, doctored, onboard --skip done).
  • No secret named QA_TMP_SECRET, QA_AGENT_SECRET, QA_RENAMED_SECRET or QA_BACK_SECRET exists (control-openhands api GET /api/settings/secrets).
  • F14.agent-access, F14.rename, F14.edit-value and F14.agent-request need an active LLM profile (control-openhands llm preset deepseek).
  • No secret named QA_REQ_SECRET or QA_REQ_CANCEL exists, for F14.agent-request.

Scenario F14--cipher-mismatch-refuses-mutation · Permalink · Source

Given

Use F14’s prerequisites and the common setup. Follow the family’s order when a script uses an earlier fixture or says “as above”.

Do — reading outline

  1. Do
    This is an external-state fixture, not a credential test. Arrange two own dummy secrets and a dummy loopback LLM key; privately back up the run-owned encryption-key, settings.json and secrets.json. Replace only the own cipher file with a newly generated value (never display it), restart and doctor. After bootstrap, restore the old encrypted store bytes under the replacement cipher to isolate the UI write. Add a new dummy secret through the real Secrets form, and inspect only boolean preservation metadata / availability of the old dummy value privately. Independently restore the encrypted settings baseline and change Sound Notifications through Application → Save. Expected: reject writes when existing encrypted state cannot decrypt, preserving it. Known failure, reproduced 2026-10-12 (OpenHands/software-agent-sdk#5622): the secret create succeeds and rewrites an old entry while its dummy value is unavailable (getter 404, name still listed); two unrelated settings saves persist the old LLM key as null. Repeat with a fresh replacement cipher. Immediately restore the original cipher and both stores in finally, restart and doctor; original state must be readable again. This drives secret creation and settings Save, not every edit/delete permutation. Keep all cipher bytes, values and raw store snapshots private.

Expect

adding a secret persists it; it is listed after a reload.

editing the description with the value left blank keeps the stored value; Save stays disabled until something changes.

  • The value editor is a plain textarea, not a password field: use dummy values only, and never ask the agent to print a real secret.

Before you start

Use an OpenHands checkout at the source revision, with Node 24+, installed npm dependencies, uv / uvx, and a supported Chromium browser. The verification skill is the complete setup contract.

export PATH="$PWD/.agents/skills/verify-openhands/scripts:$PATH"
export OH_VERIFY_RUN=$(control-openhands launch --new --print-run)
control-openhands doctor
control-openhands onboard --skip
# Configure a model only for a scenario that needs one:
control-openhands llm preset deepseek
# When the run is complete:
control-openhands stop

F01 walks onboarding instead of skipping it. No-model checks run before model configuration. Keep OH_VERIFY_RUN set so commands address your own run. Desktop is 1440 × 1000; phone is 390 × 844. Model-backed checks need the configured provider key and budget.

Recipes run in source order within each family and can share fixtures. The page preserves that order; “as above” is a dependency on an earlier case. Setup commands and API writes arrange state. They do not prove a UI path. Follow the family cleanup steps.

A known failure preserves the intended expectation beside the observed defect. Executable known-bug blocks use xfail for a reproduced symptom and xpass when it stops reproducing. Cloud accounts, enterprise capabilities and other unavailable prerequisites remain explicit. “Not run” is different from “blocked”.

The maintained map describes application behavior at its pinned revision. Once a fix is verified in the application version under test, remove the obsolete failure note and keep the normal expectation. Dated evidence belongs in the backfill ledger.
