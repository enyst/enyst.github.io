Architecture

Slack no longer depends on the legacy /turns protocol in this design. An accepted Slack event becomes durable intake, the TypeScript OpenHands agent-server owns the conversation and agent events, and a separate outbound subsystem performs the Slack side effect.

Why Slack Is Greenfield

The earlier Slack app existed to exercise Slack Events API and Socket Mode. It was never an in-use production bridge, so it has no compatibility obligation to the old immediate request/reply shape.

The useful Slack-specific pieces remain: Socket Mode, DMs and mentions, thread context, access policy, duplicate suppression, acknowledgement reactions, and message splitting. The execution path itself was rebuilt around durability.

Durability Contract

Inbound

Slack event
→ stable source message identity
→ durable intake row
→ deterministic agent event id
→ append with run=true
→ done / retry / failed

A lost append response is safe to retry because the same Slack message produces the same agent event ID.

Outbound

durable agent event
→ syncDeliveryOutbox()
→ durable delivery row
→ claim lane head
→ validate
→ mark send_attempted
→ Slack API call
→ done / failed / delivery_unknown

Once send_attempted is durable, an exception is treated as ambiguous. The dispatcher does not blindly repeat a Slack post that may already have landed.

Conversation and Lane Identity

One Slack DM or thread maps to one durable lane:

channel:slack:{team_id}:{channel_id}:{thread_ts-or-root}

The first authoritative relay generation is intentionally isolated from earlier shadow experiments:

database: ~/.smolpaws/coordinator/slack-relay-v1.db
conversation namespace: slack-relay:v1

This prevents initial catch-up from rediscovering historical shadow responses and posting them into Slack.

Reply Policy

The first canary synchronizes the agent's normal terminal finish response into the delivery outbox. A normal Slack answer does not require a Slack-specific send_message tool.

The extraction policy remains replaceable. Explicit outbound-intent events can later support progress updates or multiple messages without changing the Delivery Dispatcher.

Verification

The focused Slack suite includes a deterministic end-to-end test using:

  • the real in-process TypeScript OpenHands agent-server;
  • a scripted LLM response that calls the real finish tool;
  • real SQLite coordinator state;
  • syncDeliveryOutbox() and the Outbound Relay;
  • the Delivery Dispatcher and Slack Delivery Target boundary;
  • assertions that intake and delivery both settle durably.

Live Liberty Labs Canary

A test mention reached the installed paws bot, but its reply was the legacy fallback 🐾 Done — nothing to report back.. That response proves the currently running process still uses the old /turns runtime. It is useful deployment evidence, but not a successful test of the new relay.

The live canary completes only after the local TypeScript agent-server and Slack process are restarted from the candidate checkout, followed by verification of the Slack reply, the agent-server EventLog, and the rows in slack-relay-v1.db.
