SmolPaws Slack Coordinator Canary canary

The first bridge wired end to end through the durable coordinator and the TypeScript OpenHands transpilation.
Working source: apps/slack/  ·  Relay: outboundRelay.ts  ·  Dispatcher: deliveryDispatcher.ts

Authority: current code, executable tests, and durable coordinator records. This page explains the architecture; it deliberately does not carry mutable deployment counts or claim that a particular local process is currently running the newest commit.

Overview

Slack is a greenfield canary. It does not preserve the unused legacy Slack-to-/turns shape. The app still participates in the shared bridge registry for lifecycle compatibility, but its dispatch() method is fully overridden: durable coordinator acceptance is the ingress success boundary, and the background outbound path owns the eventual reply.

Why the split exists

The system separates three facts that are often accidentally blended together:

FactOwner
What happened inside the agent conversationAgent-server EventLog
What external work must still happenCoordinator SQLite outbox
How to perform a Slack side effectSlackDeliveryTarget

The agent-server stays upstream-shaped. Queue semantics, Slack retries, lane ordering, and ambiguous external sends remain outside it.

Outbox semantics

syncDeliveryOutbox() catches a conversation up from its durable event cursor. For the first Slack canary, a successful terminal finish observation becomes one normal thread reply. The sync is safe to repeat because delivery source keys are derived from the originating agent event and destination lane.

agent event id + destination lane
              ↓
unique delivery source_key
              ↓
replay becomes a no-op

The policy seam remains explicit. Other products may choose explicit send_message actions, terminal responses, or multiple destinations without changing the store state machine.

Delivery failure semantics

The Dispatcher validates a row before crossing the side-effect boundary. Immediately before calling Slack, it durably sets send_attempted = true.

Failure pointResult
Malformed payload or missing target, before send fenceKnown failed work
Claim expires before any send attemptSafe to make ready again
Exception after the send fencedelivery_unknown; never blindly retry
Slack confirms the messagedone with Slack ts as external_message_id

Slack policy retained

  • DMs and channel app_mention events enter the app.
  • Once a thread is mentioned, follow-up replies in that process lifetime do not require another mention.
  • Stable lane identity uses workspace, channel, and thread root.
  • Thread history is bounded and permission-aware.
  • Bot messages, self-messages, and duplicate Slack event IDs are ignored.
  • Long responses are chunked before chat.postMessage.

Canary proof

A visible Slack reply is necessary but not sufficient. An older process can also answer through the retired path. A valid end-to-end canary establishes all of the following:

  1. The running checkout identifies the intended candidate commit.
  2. The TypeScript agent-server on port 8790 is healthy.
  3. The triggering Slack event has a durable intake row that reaches done.
  4. The server EventLog contains the deterministic user event and terminal agent output.
  5. syncDeliveryOutbox() creates the corresponding delivery row.
  6. The Dispatcher settles it done with the Slack message timestamp.
  7. The reply appears in the correct thread exactly once.

The read-only inspection commands and restart notes live in docs/slack/instructions.md. Credentials remain in the local environment/keychain and must never enter coordinator rows or logs.
