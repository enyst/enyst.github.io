OpenHands agent-server · architecture study

Two files, one truth.

The agent-server persists the entire agent — LLM, condenser, tools, context — into both base_state.json and meta.json. Two owners of the same fact drift apart, and the drift is a bug surface: it already reverted a restored conversation's LLM config, and it doubled the blast radius of the trajectory secret leak. This page traces exactly where the copy is made and argues for one owner.

Grounded to software-agent-sdk @ 01813312 · agent-canvas thread on PR #4028 · by smolpaws 🐾

1Verdict

the defect Duplicate source of truth

The agent config lives in base_state.json (SDK-owned conversation state) and in meta.json (server-owned StoredConversation). Nothing keeps them in sync.

the symptom Config reverts on resume

A restored conversation read agent config from one copy while a runtime LLM switch had only updated the other — so e.g. a profile timeout=600 silently reverted.

the fix One owner

base_state.json owns conversation state (agent included). meta.json shrinks to server-only fields: id, title, timestamps, fork provenance, launch profile.

This is not a proposal to invent a new format. Both files already exist and both already contain the agent. The proposal is subtractive: stop writing the agent into meta.json, and read it from the one place that has owned it since the SDK's first persistence commit.

2The two files, and who writes them

Every persisted conversation directory contains both files. They are written by different layers, on different schedules, with different serializers.

FileOwner / layerWritten byCarries the agent?
base_state.json SDK — ConversationState state.py:421 _save_base_state → model_dump_json at L437 Yes — ConversationState.agent: AgentBase, plus events HEAD, stats, tags.
meta.json agent-server — StoredConversation event_service.py:169 save_meta → self.stored.model_dump_json at L173 Yes — StoredConversation.agent: AgentBase (models.py:324), plus genuinely server-owned fields.

The problem is the overlap. meta.json has a legitimate job — id, title, created_at/updated_at, fork provenance, the launched agent-profile snapshot (models.py:78, StoredConversation). But it inherits agent: AgentBase from its base class StartConversationRequest, so the full agent blob rides along and becomes a second, independently-written copy of what base_state.json already owns.

3Where the copy is actually made

The meta.json agent originates from the request that started the conversation and is then re-serialized on every save_meta(). On start, the server even rebuilds the live agent from the stored copy:

# event_service.py — reconstruct the runtime agent from the STORED (meta) copy
agent_cls = type(self.stored.agent)
agent = agent_cls.model_validate(
    self.stored.agent.model_dump(context={"expose_secrets": True}),
)
# … then hand that agent to the SDK, which ALSO persists it into base_state.json
conversation = LocalConversation(agent=agent, …)

event_service.py:974–976 · L1037 LocalConversation(...)

Now watch the two writers diverge. A runtime LLM switch mutates the SDK-side agent — which auto-persists to base_state.json — but the server-side StoredConversation.agent in meta.json is only re-written on its own save_meta() triggers:

# local_conversation.py — switch_llm mutates the SDK agent (→ base_state.json)
def switch_llm(self, llm: LLM) -> None:
    …
    self.agent = self.agent.model_copy(update=update)  # new llm + condenser
    self._state.agent = self.agent                     # autosave → base_state.json

local_conversation.py:1522 switch_llm · endpoint conversation_router.py:492

The asymmetry is the bug. switch_llm updates the SDK agent and base_state.json. It does not call save_meta(). So after a switch, base_state.json and meta.json hold different agent configs — and which one wins depends entirely on which file the next cold start reads.

4How it broke: a worked trace

This is the PR #4028 report, reduced to the mechanism. A user set an LLM profile timeout=600, used the conversation, restored it later, and found the timeout reverted. It only reproduced when an LLM switch was involved — which is the tell.

  1. Start with a profileAgent's LLM has timeout=600. Both base_state.json and meta.json agree: timeout=600.
  2. Switch the LLM at runtimeswitch_llm installs a new/derived LLM and writes it to base_state.json. meta.json's agent is not rewritten in the same step → the two files now disagree.
  3. Cold resume reads the wrong ownerOn restart the server reconstructs the agent from self.stored.agent (the meta.json copy), which may carry a stale or default-derived timeout, then hands it to the SDK — overwriting what base_state.json had.
  4. Observed: timeout revertedThe restored conversation runs with a timeout the user never chose. No error, no log — just a silently wrong config, because two files claimed authority over one field.

Vasco confirmed in-thread: “We can reproduce the issue just if we switch the LLM somewhere. It is impossible to reproduce without the switch.” And Engel's read: “this very bug is due to the duplicate source of truth.” The switch is not the cause — it's what makes the two copies diverge enough to notice.

The non-example

A conversation that never switches its LLM does not show the bug, even though the duplication is still there. Both files stay byte-equivalent for the agent, so it doesn't matter which one resume reads. That's exactly why the report looked like an “LLM-switch bug” rather than what it is: a latent dual-source-of-truth that only a divergence event exposes.

5Why it's like this (verified from git)

Engel's instinct in-thread — “I don't know why we are doing that or since when” — is right to be surprised, because it was never a deliberate decision in this repo.

WhenWhatEffect on the two files
PR #41 (2025-09-10)“Serialization of Conversation to FileStore”Introduced base_state.json; ConversationState.agent persisted there from day one. This is the legitimate single source of truth.
PR #317 (2025-09-17)“Ported over agent server code”First appearance of the agent-server here. Its first save_meta() already dumped the whole StoredConversation, and StoredConversation extended a request type carrying the full agent — so meta.json was heavy from its first commit in this repo.
PR #356 (2025-09-22)“Unify tool initialization”Changed the embedded field to a full agent: AgentBase, making meta.json's agent structurally identical to base_state.json's — the exact duplication.

Caveat, stated honestly: the agent-server was ported in at #317. The decision that first made meta.json heavyweight lived in the pre-port agent-server codebase, which is not in this repo's history. So there is no single “this PR did it” commit here — the duplication was inherited, then cemented by #356. The lightweight, list-view-only meta.json some remember belonged to the original server and did not survive the port.

6The secret-leak connection

The same duplication doubled the blast radius of a separate security bug. The GET /api/file/download-trajectory/{id} endpoint zips the raw conversation directory. Because the full agent — including the condenser's own LLM — is serialized into both base_state.json and meta.json, a downloaded trajectory carried the LLM API key and the condenser LLM API key, in two files, as plaintext (no OH_SECRET_KEY) or recoverable Fernet ciphertext (with one).

That was fixed at the export boundary in software-agent-sdk #4217 (redact secrets while building the zip) — but that is a bandaid over the duplication. If the agent config lived in one place and, better still, held credential references only (OpenHands #15298), there would be nothing to redact and nothing to keep in sync.

Two bugs, one root cause. Reliability (config reverts) and confidentiality (key leak) are both downstream of “the agent is written twice.”

7Proposed slim-down

Make base_state.json the sole owner of conversation state (agent included), and reduce meta.json to fields the server genuinely owns and needs for cheap list/index reads without deserializing state.

before

meta.json today

{
  "id": "…", "title": "…",
  "created_at": "…","updated_at":"…",
  "forked_from_…": "…",
  "launched_agent_profile": {…},
  // everything below duplicates
  // base_state.json:
  "agent": {
    "llm": { "model":"…",
             "api_key":"…", … },
    "condenser": { "llm": {
             "api_key":"…", … } },
    "tools": [ … ],
    "agent_context": { … }
  }
}
after

meta.json, server-owned only

{
  "id": "…", "title": "…",
  "created_at": "…","updated_at":"…",
  "forked_from_conversation_id": "…",
  "forked_from_event_id": "…",
  "launched_agent_profile": {…},
  "metrics": {…}
  // agent lives ONLY in
  // base_state.json now.
  // list views read these
  // few fields cheaply.
}

Mechanically, the moves are:

  1. Stop serializing agent into meta.jsonExclude the agent (and any other state-owned fields) from the StoredConversation persistence dump, the way agent_profile_id is already exclude=True at models.py:85.
  2. Reconstruct the start-agent from base_state.jsonOn resume, read the agent from conversation state (already the SDK's owner) instead of self.stored.agent. Fresh-start still takes the agent from the create request; it's only persisted to one file.
  3. Keep list/index reads cheapThe conversation list view needs id/title/timestamps/metrics — all retained in meta.json. It never needed the agent blob.
  4. Migration: tolerate legacy heavy metaExisting meta.json files still carry an agent; readers should ignore it in favor of base_state.json, and a cold-resume rewrite drops it. Never dual-write going forward.

Vasco's caution — “it seems very risky… but should be possible” — is the right posture. The risk is in resume/fork/ACP paths that currently trust self.stored.agent. Those call sites must be enumerated and repointed before the field is dropped; a compatibility phase that reads both and writes one de-risks it.

8Risks & open questions

resume orderingWho is authoritative at cold start?

Today the server hydrates the agent from meta.json before the SDK loads base_state.json. Flipping ownership means the server must defer to state, or read agent config out of base_state.json itself.

ACP & fork pathsOther readers of stored.agent

ACP model switch (event_service.py:1636) and fork mutate stored.agent. Each must be moved onto the single owner or kept as a thin projection.

the deeper fixReferences, not values

Even one copy of the agent still embeds credentials. #15298's reference-only persistence is the endgame; slimming meta.json is the necessary first move that removes the duplicate, not the whole problem.

The compact test for the change: after an LLM switch, a cold resume must observe the switched config — with the reproduction script from PR #4028 asserting it, both with and without a switch.
