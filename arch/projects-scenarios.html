Projects, end to end: three real projects, run live

Projects lets a person work one level up: a coordinator they talk to, workers that do the work, and a board that says what needs them. This page proves it works by running it. Three projects replayed from real OpenHands and Insider history, plus every building block, all driven in Agent Canvas with real agents doing real work. Each section has a short narrated video. Where something broke, it says so, and says what happened next.

How it was run

The stack was the two Projects pull requests together: SDK #6602 (Agent Server, up to 95dadd7) and Canvas #19495, with Insider main installed as a Canvas app. The coordinator and the workers ran the new project_coordinator and project_worker prompts and their predefined profiles (the design, landed in #6602 at 67c1038). Agents ran on DeepSeek. Every UI step was driven with the control-openhands CLI in the Paper theme and recorded, and the server side was checked with verify-agent-server.

The projects are replays. Each one starts from a local copy of a real repository at the commit just before the real work happened, with no remote and the later history removed, so nothing reached the real repositories and the agents couldn't peek at the answer. That lets us compare each worker's fix with the one that actually merged.

1. Turn Projects on

Projects and conversation reactions are switched on from Settings › Experimental (mentions come with Projects). The first project seeds two profiles from the person's active one: Project coordinator (terminal, file editor, task tracker and the project tools, no browser) and Project worker (the person's tools, without the power to start more conversations). Neither is overwritten later. Whatever profile a coordinator or worker runs, the server gives it its role in the system prompt.

2. Project 1: an SDK bug bash

Four edge-case bugs from SDK issue #6348, on the SDK as it was before they were fixed: a search pattern read as a command-line flag (#6537), file:// URLs sliced wrong (#6482), stale cached text after a binary write (#6534), and a lost first-line indent in commit diffs (#6538).

We gave the coordinator all four reports in one message. It started one worker per bug and ended its turn, as its prompt tells it to. Each worker found the cause, wrote a regression test that failed first, fixed it, and reported back. The coordinator reviewed every diff without touching the workers' worktrees and sent one summary with two decisions for us. All four fixes match what merged in substance. When we asked for one more test case, the coordinator sent it to the worker that owned that branch instead of doing it itself. Three cards resolved on their own (the judge was 85 to 92% sure); we resolved the fourth by hand and reopened one from its banner.

3. Project 2: scoped secrets

A feature rather than fixes: scoped secrets, issue #5672, which merged as #6276. It touches the model, the system prompt and the agent. We asked to approve the exact prompt text first. The coordinator split the work, started only the parts that didn't depend on that text, and saved its proposal as a project file. The card waited under Needs you until we approved it with one change.

Then we dropped into a busy worker and said “wait, actually, also test the round trip”. The worker did it, but only after its running test command finished, a few minutes later, and it didn't react with a 👍. Both are listed under what's still open. At the end the coordinator merged the three branches locally to check that they fit together, and wrote our rule into project memory.

4. Project 3: Insider

The same server, seen through the Insider app. We installed Insider from GitHub in Customize › Apps and trusted it. Then we gave the Insider Cat three fixes the Projects review found in Insider itself (#58, #59, #60, the review's I2 gap), on a local copy from before they landed. The Cat started a real project on the server, with coordinator tools, and three workers. Its board grouped them the way the server does. One worker asked whether to merge its branch with the others; we answered from the card and came back.

5. Project files and memory

We uploaded a release checklist on the bug-bash project page and asked whether the four branches met it. The coordinator listed the project's files, read ours, checked every branch, and found the real gap: no commit named the issue it fixed. Memory works the same way in the other direction. The rule we gave the coordinator in the scoped-secrets project showed up in the next worker's <PROJECT> block, in its system prompt.

6. Agent Server restarts

We restarted Agent Server while a worker was running. Projects, the board and every conversation came back, the interrupted worker showed under Needs you, the coordinator was told, and one sentence from us got the worker going again. Two things were wrong on the way. The first try reported the pause as ours (“Paused by the person”), fixed in 14b3f7c. On the second, the worker was mid-command and came back worded like a crash, fixed in 95dadd7. Run again live after the fix, the worker came back paused, and the coordinator said it was “paused by the server restart, not by you”.

7. Turn Projects off

With the switch off, the sidebar entry goes and the Projects page says where to turn it back on. Nothing is deleted: on again, all three projects are still there, with their boards.

What's still open

A message to a busy worker waits for its running command. “Wait, actually” is delivered only when the current tool call ends, which can be minutes for a test run. The cause is the SDK's step lock; it's going to Engel as its own question rather than a quiet fix.
  • Agents don't react 👍 to a “wait, actually” unless AGENTS.md nudges them, the same finding as the reactions film. They do act on the content.
  • The board doesn't show the coordinator's own state, and the projects list doesn't show which project needs you.
  • A resolved card keeps showing its old ask text.
  • The Canvas profile editor shows “OpenHands default” as the system prompt for the two project profiles, though the server gives them their role.
  • Insider: the project is named after the whole first message; the Cat runs the person's active profile, so it has a browser; updates are labelled “Another conversation”; the page needs a reload after the app is enabled.
