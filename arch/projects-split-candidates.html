What could split out of the Projects PR

A fresh read of software-agent-sdk #6602, looking for pieces that would earn their place on main without Projects. Three do. One more might, and should be checked first. The rest is plumbing that only Projects calls, and it should stay where it is.

“maybe separately (separately, you could make a new thread even just so it thinks anew) suggestions if theres anything we could separate out”

Read at #6602 head ba97cee against main f1eedd7. The PR is 82 files and about 16,800 added lines: roughly 8,400 of code, 7,200 of tests, 760 of docs and prompt snapshots, and 540 of TypeScript client. Already split out and not repeated here: flags #6759, reactions #6609, ask_user #6852, mentions #6851, exceptions #6910 and #6912, the flag cache #6936, and #6922. The auto-resolve judge was considered before and stays out for the same reason as then: nothing on main would call it.

The test for each piece was the same. Does main get something from it today, with Projects off? Can it be reviewed on its own? And can it be cut from main without dragging project code along? Each split-out PR would be opened from main, with #6602 keeping its copy until it merges, as with the others.

Split these

1Messages from someone other than the user

Recommend · the biggest one · after #6912

When anything but the user posts a message and asks for a run, it should never approve the user's pending actions or resume work the user paused. #6602 adds that rule for every sender, plus a way to say who sent the message.

What it holds
admission_refusal and the typed refusals ConversationAlreadyRunning, GoalAlreadyRunning and HeldForUser (event_service.py). On POST /api/conversations/{id}/events: refuse_pending_confirmation, sender_conversation_id with its header line, and a SendMessageResponse that says whether the message ran (started, queued, a held status, or not_run). The sender constants in conversation/types.py: conversation_sender, CONVERSATION_SENDER_PREFIX, GOAL_LOOP_SENDER, HELD_FOR_USER_STATUSES. A child's first message recorded as sent by its parent. The matching TypeScript types.
Why on its own
Today a run asked for on a conversation waiting for confirmation approves its pending action. Any client that talks to a conversation for someone else hits that: automations, Voice, and the Insider Cat, whose prompt already tells it to send refuse_pending_confirmation and sender_conversation_id (enyst/insider extension.js:421). Those fields exist only in #6602. A released server's SendMessageRequest silently ignores fields it does not know, so the Cat's careful message runs unguarded there. start_child_conversation is on main too, and its task message would finally record who sent it.
What stays in #6602
The project rule in sender_message_header (a project's conversations reach only their own project, and the coordinator gets its own wording). On main the header names “another conversation”. Also run_saved_message_when_free and keep_goal_loop, which only project wake-ups use.
Depends on
#6912, because the three exception classes belong in its new exceptions.py. Open it once #6912 merges, not on top of it.
Size
My estimate: about 350 lines of code and a similar amount of tests, much of it already written in #6602 (commit d31af0b for the typed refusals). If that feels large, the typed refusals alone are a clean refactor in the spirit of #6910 and could go first, and the guard after it merges.
Flag
Opt-in request fields, so nothing changes for clients that don't send them. The one visible change is the child's task showing its parent as sender.

2Find the open question without reading the whole log

Recommend · small · and it fixes more on main than #6602 does

Your rule is that nothing reads a whole event log. main still does it to answer one small question: is there an unanswered ask_user?

What it holds
find_pending_ask_back in sdk/event/ask_user.py: one pass, newest first, stopping at the question or the user's latest message, so it can take state.walk_back() lazily.
Why on its own
On main, find_pending_ask is fed the whole active branch in local_conversation.py (three places), event_service.py (the goal loop check), and the whole log in goal/runner.py:54 (conversation.state.events). #6602 only fixed the agent server's call. A PR from main would fix all five, with ask_user (#6852) already released.
What stays in #6602
The coordinator parts of the same function: for_conversation, and treating a coordinator-delivered answer as closing the question.
Depends on
Nothing. walk_back is on main.
Size
About 40 lines in ask_user.py, six call sites, and tests.

3Show new tags as soon as they are saved

Recommend · a bug fix, so its own PR by the standing rule
What it holds
Commit 81147dd: GET /api/conversations/{id} reads tags from meta.json instead of base_state.json (conversation_service.py:443).
Why on its own
A tag PATCH writes meta.json at once, but a running conversation saves base_state.json only when its run lets go of the state lock. Until then the PATCH looks lost. That happens on main for anyone who tags a running conversation, Insider's tags included.
Depends on
Nothing.
Size
Eight lines and an 18-line test, which today lives in test_projects_router.py and would move to the conversation tests.

Check first

4A shutdown pause is not a crash

Maybe · only if it reproduces on main

close() leaves a .paused_by_shutdown mark when it pauses a running run, and on load a conversation still marked RUNNING comes back PAUSED with an honest message, instead of ERROR and “this may indicate a fatal memory error”. Its main consumer is Projects: the coordinator's catch-up after a restart names the restart instead of blaming the user (commit 14b3f7c). On main, close() already pauses before it cancels, so a graceful shutdown may already end PAUSED. I did not reproduce it. If a stop of the server on main does leave conversations in ERROR with the crash message, the load-time half is a bug fix worth its own small PR. If not, it stays.

What it would leave

With the three split out, #6602 sheds its only changes to the shared send path and to the ask lookup, which are the parts a reviewer outside Projects would worry about most. What remains is Projects itself: the store and routes, the service, turn tracker and board, wake-ups, the tools, the prompts and the client. Behind the flag, and reviewable as one feature. The order I would suggest: 3 and 2 now, since they depend on nothing; 1 once #6912 merges.
