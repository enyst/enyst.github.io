Agent Canvas · DigitalOcean · design proposal · 19 October 2026

People sign in. Agents use keys.

How Agent Canvas should hold a DigitalOcean connection. One sign-in, kept in the keychain of the machine that runs Canvas. The same flow in the desktop app and the browser. And narrow keys for agents that want to use your DigitalOcean sessions from outside Canvas.

Today’s behavior checked live · revision 8d39305Proposal · nothing implementedDigitalOcean OAuth checked against its live metadata
If you only read one thing

The machine that runs Canvas owns DigitalOcean access. People sign in once with DigitalOcean OAuth: the authorization-code flow with PKCE, which DigitalOcean now offers to apps that can’t keep a secret, with refresh tokens. The host keeps the grant in the macOS Keychain or its equivalent, so a restart signs nobody out. The desktop app and the browser share this one bridge.

Agents get Canvas agent keys: one team, a short list of permissions, revocable, and never a DigitalOcean token. An agent that doesn’t run near Canvas uses its own DigitalOcean token and talks to DigitalOcean directly.

Companion page: Keep DigitalOcean connected, published the same evening. It covers sign-in and restore in more depth. This page adopts its recovery rules and adds the agent side. Where the two agree and differ.

01 / What happens today · checked on 19 October

The browser forgets you. The desktop app remembers you its own way.

Canvas has two DigitalOcean bridges today. In the desktop app, the Electron main process holds the credentials, encrypted with Electron’s safeStorage. In the browser build, the Canvas server holds them in memory. The two share the service code in scripts/mars-tunnel-bridge.mjs, but each has its own storage, its own sign-in and its own reach.

What a person runs into, in the order they meet it (browser build, driven with control-openhands):

  1. A token is the only way in. The hint under the field says to use a token “when your organization does not allow third-party sign-in”, but this page offers no other sign-in.
  2. The account line names the token, not the team. teamName is null for every connection, because nothing asks DigitalOcean which team the token belongs to.
  3. No warning that the sign-in won’t last. The bridge reports isPersistent: false, but this panel doesn’t say so. Only the account bar in Manage Backends’ Managed Agents view shows the warning.
  4. A restart signs you out. After control-openhands restart, getAuthState() returns {"connections":[],"active":null} and the sign-in form is back. According to the bridge’s own notes, a DigitalOcean backend you had selected stays in the browser’s backend list with no credential behind it until someone signs in again.
  5. The cookie breaks too. The /mars cookie secret is random per process, so a browser’s existing cookie stops working after a restart. A maintainer’s comment on #18604 raised this.

Not checked here: connecting a session, because in this sandbox the tunnel’s WebSocket bypasses the proxy that supplies DigitalOcean credentials. Also not checked: Electron’s OAuth window, since there is no display. Those rows come from the source.

DigitalOcean’s OAuth has moved on. Today’s desktop sign-in uses the implicit grant (response_type=token). mars-oauth.mjs says it chose this because “DigitalOcean documents no PKCE support”. DigitalOcean’s live authorization-server metadata now advertises only code, plus PKCE (S256), the refresh_token grant and dynamic client registration.

According to its OAuth reference, apps that can’t keep a secret (“public clients”) get one-hour access tokens and single-use refresh tokens. Loopback redirect addresses “match on any port”. The token response names the team (info.team_uuid, info.team_name). That fixes three of today’s problems at once: no 30-day re-login, no fixed port 53682, and a team name for the account line.

02 / The model

One host holds the keys. Everyone else asks it.

The Canvas host is the machine running Canvas: the desktop app on your Mac, or npx @openhands/agent-canvas on a Mac mini, a Linux box or a container. It is the only place a DigitalOcean credential exists.

  1. People (browser or desktop app) reach the Canvas host with the Canvas session key. They approve Canvas on DigitalOcean once.
  2. The Canvas host keeps the DigitalOcean grant in the OS keychain, refreshes it, and opens tunnels to sessions.
  3. Agents near Canvas reach the host with an agent key and work in sessions through its proxy.
  4. Agents elsewhere use their own DigitalOcean token with DigitalOcean directly. Canvas isn’t involved.

Five rules the code keeps

  1. DigitalOcean tokens stay in the host process. No page, agent, log line or RPC response carries one.
  2. Secrets go in the OS keychain, and descriptions go in a file. When a host has no keychain, Canvas says where it keeps the sign-in instead of pretending.
  3. One bridge serves the desktop app and the browser. Electron stops running its own.
  4. A session key and an agent key are different keys. The session key unlocks all of Canvas. An agent key unlocks only one team’s DigitalOcean sessions, with the permissions a person chose.
  5. Canvas dials only what someone is using. Every probe counts as sandbox activity and keeps a sandbox awake, and billing. So, as today, nothing polls sessions in the background.

The sign-in belongs to the host, not to a browser tab. Every browser that holds this Canvas’s session key uses the host’s DigitalOcean sign-in. That is already true today, in memory. Keeping it in the keychain makes it last, so the UI names the host it lives on.

03 / UX for people

Sign in once, in the browser you already use.

The same screens appear in the desktop app and the browser. The sign-in button comes first. The token field moves behind a disclosure, for organizations that don’t allow third-party apps. Every signed-in view says where the sign-in is kept.

04 / UX for agents

An agent key has a name, a team and a short list of permissions.

A person creates a key in Canvas and gives it to an agent. Canvas shows when the key was last used, and anyone signed in can revoke it. The agent never sees a DigitalOcean token: it talks to the Canvas host, which signs every DigitalOcean call with the person’s grant.

05 / Code design

One bridge in the Canvas server, with three stores and two front doors.

The bridge moves entirely into the Canvas server process that fronts the page: scripts/ingress.mjs in the full stack, or scripts/static-server.mjs on its own. People reach it through /mars/rpc with the session key. Agents reach it through /mars/v1 with agent keys. Both end in the same tunnel registry and session proxy.

Sign-in, step by step

  1. pagebeginSignIn({ origin }) on click. hostPicks the redirect mode (section 03), creates state and a PKCE verifier (memory, 10 minutes, single use), and returns { attemptId, authorizeUrl, mode }.
  2. pageOpens about:blank synchronously in the click handler, so popup blockers allow it, then points that window at authorizeUrl. Electron already sends such windows to the system browser; the OpenHands Cloud device login uses the same route.
  3. personPicks the team on DigitalOcean and approves.
  4. DigitalOceanGET /mars/oauth/callback?code&state on the Canvas origin. In paste mode, the page sends the pasted address with completeSignIn instead. The route needs no cookie: it may arrive in a system browser that has none. The single-use state and the PKCE verifier protect it.
  5. hostPOST /v1/oauth/token with the code and verifier. It receives a one-hour access token, a refresh token and info.team_uuid and info.team_name. It then checks that the token can list sessions, and writes the vault before the metadata.
  6. pageawaitSignIn(attemptId), a long poll, resolves, and the panel lists the team’s agents. The callback tab says “Signed in to DigitalOcean as My Team. You can close this tab.”
Refreshing without racing yourself

Refresh tokens are single-use, and a refresh invalidates the previous access token. Two refreshes in flight would leave the host holding a dead token. So each process refreshes once per connection at a time, a lock file covers several Canvas processes sharing one keychain, and the new pair is saved before it is used.

async function accessToken(id) {
  const s = await vault.read(id);
  if (s.kind === "pat") return s.token;
  if (msLeft(s) > 60_000) return s.access_token;
  return singleFlight(id, () => withFileLock(`digitalocean-${id}`, async () => {
    const fresh = await vault.read(id);                 // another process may have refreshed
    if (msLeft(fresh) > 60_000) return fresh.access_token;
    const r = await oauth.refresh(fresh.refresh_token); // the old refresh token dies here
    if (r.error === "invalid_grant") {
      connections.setStatus(id, "needs-sign-in");      // screen E; agent calls get 401 sign_in_required
      throw new SignInRequired(id);
    }
    await vault.write(id, { ...fresh, ...r });          // persist before use; if this throws, the old
    return r.access_token;                              // token is already spent: report needs-sign-in, never success
  }));
}
Restoring a DigitalOcean backend without overwriting it

Adopted from the companion page. A persisted credential removes the most common restore failure, but not every one. Restore has to repair whichever step is missing while leaving the saved destination alone.

  • Each DigitalOcean backend record carries marsConnectionId next to marsSessionId. Reconnects use that connection, never “whichever team is active”. When an old record has no connection ID, Canvas checks which team owns the session, and asks the person if it can’t tell.
  • Root picks a DigitalOcean recovery screen for a managed DigitalOcean backend: unlock the host, sign in again (screen E), keychain locked, session unreachable, or session deleted. The generic local API-key form never edits a managed DigitalOcean record. That form is the path a maintainer flagged on #18604.
  • Restore wakes only the selected session, and it never creates a replacement because a restore failed.

The desktop app joins the host bridge

Electron stops creating its own bridge in the main process, and the preload drops window.marsBridge. Electron also stops passing marsWebBridge: false to the stack. The page then finds the bridge at /mars/health, exactly as a browser does.

Before the stack starts, a one-time migration reads mars-credentials.json (v1) from the app’s data folder. It decrypts each token with safeStorage, writes vault entries and v2 metadata, and renames the old file to .migrated. Implicit-grant tokens move as access-only connections, and they renew through the new sign-in when they expire.

The trade: DigitalOcean in the desktop app now needs the ingress process, which the stack starts after waiting for the local Agent Server. The desktop app already opens its window from that ingress, and already shows a startup failure when the Agent Server doesn’t come up. So no setup that works today loses DigitalOcean. Letting DigitalOcean work while the local Agent Server is down would be a separate improvement.

Why restarts stop breaking the cookie

The cookie value becomes HMAC-SHA256(session key, "mars-web-cookie/v1"). It stays valid across restarts and changes when the key rotates, so control-openhands restart --rotate-key still invalidates it, as it should. Nothing new is stored.

06 / Security

What could go wrong, and what stops it.

ConcernAnswer
A token reaches the pageRPC answers carry metadata only. The callback page shows the team name only.
A forged callbackstate is single-use and expires after 10 minutes. The PKCE verifier never leaves the host. redirect_uri is pinned per attempt. When the callback returns to the browser that started it, the host also checks a short-lived attempt cookie (SameSite=Lax, as the companion page proposes). The desktop app’s system-browser return has no such cookie, and relies on state plus PKCE, the native-app pattern of RFC 8252.
A pasted callback address leaksUseless without the verifier. The code is single-use.
Someone reads refresh tokens from diskThey live in the keychain. The fallback file is encrypted. The metadata and agent-key files hold no secrets.
An agent key leaksShown once, hashed at rest, limited to one team and its permissions, expires, shows when it was last used, can be revoked. The oh_dok_ prefix makes it findable by secret scanners.
Agent keys sent over a networkCanvas binds to 127.0.0.1 by default. A non-loopback bind already requires the session key. For agent traffic across machines, use TLS or a private network such as a tailnet.
An agent reaches another team’s sessionThe session must belong to the key’s connection (the tunnel owner) and to an allowed agent.
An agent runs up a bill“Start new sessions” is opt-in, and nothing polls sessions in the background.
A DNS-rebound or cross-origin pageUnchanged: the Host check on loopback binds, and cross-origin refusal on /mars/*. The callback route takes no Origin-based shortcuts.
07 / Rollout and checks

Three steps, each useful on its own.

Step 1

Stay signed in

SecretVault and ConnectionStore behind today’s browser token sign-in. The HMAC cookie. Team name and storage line in the panel. Desktop unchanged.

A person notices: restarting Canvas no longer signs them out.

Check: the failing row from section 01 turns green. Sign in, run control-openhands restart, and the panel still lists agents. Linux CI has no Secret Service, so the run uses OH_CANVAS_SECRET_STORE=file. A Mac pass proves the Keychain path.

Step 2

People sign in with OAuth, everywhere

PKCE on the Canvas origin. The three redirect modes. Team identity. Refresh and the renew banner. Electron joins the host bridge, with the migration.

A person notices: “Sign in with DigitalOcean” in the browser, and no monthly re-login.

Check: a browser sign-in on loopback; paste mode on a --host 0.0.0.0 run; a desktop sign-in after migrating an old safeStorage file; and the renew banner after a refused refresh.

Step 3

Agents use keys

AgentKeyStore, /mars/v1, the WebSocket auth front, the Agent access screens and “Save as a Canvas secret”. Documentation, plus a reusable skill in OpenHands/extensions that teaches agents the contract.

A person notices: their own agent can open a DigitalOcean session without a DigitalOcean token.

Check: create a key, list agents with curl, connect, and run a command through RemoteWorkspace. Then: a see-only key gets 403 on connect, a revoked key gets 401, and sign-out pauses the keys.

Later

The session’s public ingress URL as a second transport, once DigitalOcean’s WebSocket fix (microvm#1920) ships. An MCP endpoint over /mars/v1. Scoped keys for the rest of Canvas, reusing the same store.

Per AGENTS.md, feature-map and recipe updates for verify-openhands go in their own PR, after the product change.

08 / Alternatives considered

Other ways to get here.

Keep two bridges and add a keychain to the browser one

Smaller. But agents still couldn’t reach DigitalOcean through the desktop app, and the two sign-ins would keep drifting: OAuth exists in only one of them today.

Keep credentials in each browser

That puts a token-equivalent in the page, and harness-api has no CORS anyway. It also leaves agents out, and every browser signs in separately.

Agents only ever use DigitalOcean tokens

Works from anywhere. But every agent would reimplement the port-forward tunnel and hold a team-wide credential, with no per-agent limits and no record in Canvas. Kept as the path for agents far from Canvas.

A hosted token exchange with a client secret

Not needed now that DigitalOcean supports PKCE for public clients. It would add a third party that sees every user’s tokens, which is the wrong direction for an open, self-hosted tool.

Keep the implicit grant

DigitalOcean’s live metadata no longer advertises it. Its tokens can’t be refreshed, so every agent key would stop working each month until someone signs in again.

Encrypted file everywhere

One code path. But the key then sits next to the file, or in an environment variable, on every desktop. The keychain is what the OS offers for this. The file stays as the fallback for hosts without one.

09 / Next to the companion page

Two proposals, mostly one design.

Keep DigitalOcean connected reached the same core conclusion independently: authorization code with PKCE, refresh tokens, OS-protected storage, one renewal at a time. Where the two differ:

Recommendation

  1. One bridge. The desktop app already serves the UI, the Agent Server and automation from its localhost ingress, behind the session key. Hosting /mars there too adds no new kind of exposure, and it is the only way an agent on a desktop host can reach DigitalOcean through Canvas. Two bridges also mean two sign-in implementations; OAuth existing in only one of them is how today’s drift began.
  2. Derived cookie first, per-browser sessions later. The derived cookie is the smallest change that fixes restarts. The companion page’s per-browser store is the better end state once Canvas offers per-browser sign-out, or several people share a host.
  3. Paste-back as a fallback, not a path. Show it alongside the better setups: an HTTPS address, as the companion page advises, or an SSH forward that keeps the page on loopback.
10 / Open questions

Things to settle with DigitalOcean and the maintainers.

  1. One shipped OAuth client, or one per host? Dynamic registration per host needs no configuration, and lets a self-hosted HTTPS Canvas register its own callback. A shipped public client ID gives DigitalOcean one app to recognize. Recommendation: register per host by default, with DO_OAUTH_CLIENT_ID as the override. Ask DigitalOcean how dynamically registered clients appear on the consent screen.
  2. Scopes and refresh-token lifetime for public clients. Does a dynamically registered client get agent_harness_session:read and :operate? The reference doesn’t say how long a refresh token lives, which decides how long a host can sit idle before someone signs in again.
  3. Plain-HTTP, non-loopback callbacks. Canvas won’t register them either way. The question is only what to document.
  4. The name of the agent contract. /mars/v1 keeps today’s prefix, but MARS is DigitalOcean’s internal name. /digitalocean/v1 would read better to people writing agents.
  5. Should /mars/v1 accept the session key? Proposal: no, so agents get pointed at narrower keys.
