Agent Canvas · DigitalOcean · design proposal · revised 20 October 2026

People sign in. Agents use keys.

How Agent Canvas should hold a DigitalOcean connection. A sign-in kept in the keychain of the machine that runs Canvas, so a normal restart doesn’t ask for it again. One bridge for the desktop app and the browser. And a complete path for agents, which already hold a Canvas key, to use your DigitalOcean sessions.

Today’s behavior checked live · revision 8d39305Proposal · nothing implementedRevised after smolpaws’s review
If you only read one thing

The machine that runs Canvas owns DigitalOcean access, through one bridge for the desktop app and the browser. People sign in with DigitalOcean OAuth: the authorization-code flow with PKCE, which DigitalOcean now offers to apps that can’t keep a secret, with refresh tokens. The host keeps the grant in the macOS Keychain or its equivalent, so a normal restart doesn’t ask anyone to sign in again. A grant DigitalOcean expires or revokes still asks once more.

Agents use the Canvas session key they already have. No new kind of key. The work is to make that path complete: the sign-in survives restarts, the stock clients’ event socket works through the proxy, and a session an agent connects gets the same sandbox preparation as one a person opens.

Decided on 20 October, after review.

  1. One host bridge for the desktop app and the browser. smolpaws, who first proposed two, agrees.
  2. The browser’s bridge cookie is derived from the session key. It’s the simple choice: it can’t sign out one browser, and rotating the key signs out every browser. Per-browser sessions stay a later option.
  3. Agents keep using the session key; there are no scoped agent keys for now. An agent that already holds the full key isn’t limited by an extra narrow one.
  4. For remote browsers, OAuth ships first where DigitalOcean’s reply lands by itself. Paste-back waits for a proof (section 03).
  5. Wording: “stay signed in across restarts”, not “sign in once”.

Companion page: Keep DigitalOcean connected, published the same evening. It covers sign-in and restore in more depth; this page adopts its recovery rules. Where the two agree and differ.

01 / What happens today · checked on 19 October

The browser forgets you. The desktop app remembers you its own way.

Canvas has two DigitalOcean bridges today. In the desktop app, the Electron main process holds the credentials, encrypted with Electron’s safeStorage. In the browser build, the Canvas server holds them in memory. The two share the service code in scripts/mars-tunnel-bridge.mjs, but each has its own storage, its own sign-in and its own reach.

What a person runs into, in the order they meet it (browser build, driven with control-openhands):

  1. A token is the only way in. The hint under the field says to use a token “when your organization does not allow third-party sign-in”, but this page offers no other sign-in.
  2. The account line names the token, not the team. teamName is null for every connection, because nothing asks DigitalOcean which team the token belongs to.
  3. No warning that the sign-in won’t last. The bridge reports isPersistent: false, but this panel doesn’t say so. Only the account bar in Manage Backends’ Managed Agents view shows the warning.
  4. A restart signs you out. After control-openhands restart, getAuthState() returns {"connections":[],"active":null} and the sign-in form is back. According to the bridge’s own notes, a DigitalOcean backend you had selected stays in the browser’s backend list with no credential behind it until someone signs in again.
  5. The cookie breaks too. The /mars cookie secret is random per process, so a browser’s existing cookie stops working after a restart. A maintainer’s comment on #18604 raised this.

Not checked here: connecting a session, because in this sandbox the tunnel’s WebSocket bypasses the proxy that supplies DigitalOcean credentials. Also not checked: Electron’s OAuth window, since there is no display. Those rows come from the source.

DigitalOcean’s OAuth has moved on. Today’s desktop sign-in uses the implicit grant (response_type=token). mars-oauth.mjs says it chose this because “DigitalOcean documents no PKCE support”. DigitalOcean’s live authorization-server metadata now advertises only code, plus PKCE (S256), the refresh_token grant and dynamic client registration.

According to its OAuth reference, apps that can’t keep a secret (“public clients”) get one-hour access tokens and single-use refresh tokens. Loopback redirect addresses “match on any port”. The token response names the team (info.team_uuid, info.team_name). That fixes three of today’s problems at once: no 30-day re-login, no fixed port 53682, and a team name for the account line.

02 / The model

One host holds the keys. Everyone else asks it.

The Canvas host is the machine running Canvas: the desktop app on your Mac, or npx @openhands/agent-canvas on a Mac mini, a Linux box or a container. It is the only place a DigitalOcean credential exists.

  1. People (browser or desktop app) reach the Canvas host with the Canvas session key. They approve Canvas on DigitalOcean once.
  2. The Canvas host keeps the DigitalOcean grant in the OS keychain, refreshes it, and opens tunnels to sessions.
  3. Agents near Canvas reach the host with the same session key and work in sessions through its proxy.
  4. Agents elsewhere use their own DigitalOcean token with DigitalOcean directly. Canvas isn’t involved.

Five rules the code keeps

  1. DigitalOcean tokens stay in the host process. No page, agent, log line or RPC response carries one.
  2. Secrets go in the OS keychain, and descriptions go in a file. When a host has no keychain, Canvas says where it keeps the sign-in instead of pretending.
  3. One bridge serves the desktop app and the browser. Electron stops running its own.
  4. The session key is all of Canvas, and the docs say so. Whoever holds it, a person’s browser or an agent, can also use the host’s DigitalOcean connection: list, start, connect, pause and stop sessions.
  5. Canvas dials only what someone is using. Every probe counts as sandbox activity and keeps a sandbox awake, and billing. So, as today, nothing polls sessions in the background.

The sign-in belongs to the host, not to a browser tab. Every browser that holds this Canvas’s session key uses the host’s DigitalOcean sign-in. That is already true today, in memory. Keeping it in the keychain makes it last, so the UI names the host it lives on.

03 / UX for people

Sign in, and stay signed in across restarts.

The same screens appear in the desktop app and the browser. The sign-in button comes first. The token field moves behind a disclosure, for organizations that don’t allow third-party apps. Every signed-in view says where the sign-in is kept. A grant can still expire or be revoked on DigitalOcean’s side; then Canvas asks once more (screen E).

Where does DigitalOcean send the browser back?

After you approve, DigitalOcean redirects the browser to a callback address. Which address works depends on where the browser is. Pick a case:

Sign-in return path · choose a case
Page addresshttp://127.0.0.1:8000
redirect_urihttp://127.0.0.1:8000/mars/oauth/callback
OAuth clientAny client with a loopback callback (loopback matches any port)

One click. The callback lands on Canvas itself. This ships first.

This covers the desktop app, a browser on the Canvas machine, and SSH port forwarding: there, the page address is loopback on your laptop and the forward carries the callback home.

Why warn about plain HTTP rather than block paste-back. smolpaws is right that paste-back only fixes where DigitalOcean’s reply lands, not the connection between the browser and Canvas. But Canvas can’t tell a protected link from an open one: plain HTTP over a tailnet looks the same as plain HTTP on a café network. And on an open link the bigger exposure is already there. The Canvas session key crosses it, and that key alone drives the host’s DigitalOcean connection.

The alternative such a person has today is pasting a personal access token, a long-lived credential, over the same link. A pasted code is single-use and useless without the verifier that stays on the host. So: a warning that covers all of Canvas on plain-HTTP, non-loopback pages, with HTTPS, a tailnet or an SSH tunnel as the fix; and paste-back once proven, not gated.

04 / Agents

Agents use the key they already have.

Agents in local Canvas conversations already receive the Canvas session key, as OPENHANDS_AUTOMATION_API_KEY. A personal agent on the same machine can be given the same key: it is LOCAL_BACKEND_API_KEY, or ~/.openhands/agent-canvas/api-key.txt on the Canvas host. With it, an agent can already reach the DigitalOcean bridge. So there’s no new kind of key. The work is to make that path complete, and to document it.

What works today (checked live, 20 October)

An agent sends, with the session keyResult
POST /mars/rpc/listAgentConfigsThe team’s OpenHands agents: pr18604-live, openhands-do. Without the key: 401.
POST /mars/rpc/listConfigSessionsThat agent’s sessions: one, paused.
REST through /mars/sessions/<id>/api/…Passes authentication (409 here, because the session isn’t connected).
Event-socket upgrade, key in a headerPasses authentication (409, same reason).
Event-socket upgrade, no header401. This is how the Python SDK and the TypeScript client connect: they send the key as a first {"type":"auth"} message.

A person had signed in through the UI first. Connecting a session wasn’t possible in this sandbox (section 01). Just as for people, a restart takes DigitalOcean away from agents.

Four gaps to close

  1. The sign-in must survive restarts. Step 1 fixes this for agents and people alike.
  2. The proxy’s event socket must accept first-message auth. When a request has no cookie or header, the proxy completes the handshake and waits up to 10 seconds for {"type":"auth","session_api_key":…}. It checks the key, dials the session, and pipes frames, dropping that first frame because the guest Agent Server has no key. That is the Agent Server’s own contract, so the stock clients work unchanged. Agents that use only REST don’t need this.
  3. The host must prepare the sandbox, not the browser. Canvas works around two gaps in DigitalOcean’s template: it gives the sandbox a secret key for encrypted settings, and a terminal that doesn’t use tmux. Today that runs in the browser when a person attaches a session (prepareMarsSandbox). A session an agent starts and connects skips it, and its first terminal command fails. So move it into the bridge’s connect step, for every connection, until DigitalOcean’s template fix (#18338) makes it unnecessary.
  4. Name the supported calls. The agent surface is five bridge methods plus the proxy. Document them and cover them with tests, so a UI refactor can’t break agents silently. They keep the RPC’s shape: POST /mars/rpc/<method> with {"args":[…]}.

Starting a conversation on a DigitalOcean agent

# KEY: OPENHANDS_AUTOMATION_API_KEY in a local conversation, or ~/.openhands/agent-canvas/api-key.txt on the host
B=http://127.0.0.1:8000
rpc() { curl -s -X POST "$B/mars/rpc/$1" -H "X-Session-API-Key: $KEY" -H 'Content-Type: application/json' -d "{\"args\":$2}"; }

rpc listAgentConfigs '[]'                         # configs; use those with "agent":"openhands"
rpc listConfigSessions "[\"$AGENT\"]"             # its sessions, or start one (it bills while it runs):
rpc createSession "[\"$AGENT\"]"                  # waits until READY, up to 5 minutes
rpc openTunnel "[{\"sessionId\":\"$SESSION\"}]"   # wakes a paused one → {"host":"$B/mars/sessions/$SESSION",…}

curl -s -X POST "$B/mars/sessions/$SESSION/api/conversations" \
  -H "X-Session-API-Key: $KEY" -H 'Content-Type: application/json' -d @start.json
rpc pauseSession "[\"$SESSION\"]"                 # when done

The conversation needs an LLM, either set in that session’s Agent Server settings or sent in the start request. With the OpenHands SDK, point RemoteWorkspace(host=…, api_key=KEY) at the host that openTunnel returns. Its REST calls work today; its event socket works once gap 2 is closed (checked against the SDK and Agent Server 1.56.0).

What this key can do, said plainly. The session key is all of Canvas. Whoever holds it can also start sessions, which bill, and stop them and delete agents, for the active DigitalOcean team. Only give it to agents you would let do that. As smolpaws points out, a narrower key would mean something only once agents stop receiving the full one. That’s a separate decision about the session key itself, not about DigitalOcean.

An agent that can’t reach Canvas, such as a cloud worker or CI, uses its own DigitalOcean token with DigitalOcean directly (doctl agents port-forward). Canvas isn’t involved.

Not proposed now: scoped agent keys

The first version of this page proposed Canvas-issued agent keys: named, bound to one team, with permissions to see, use, start and manage, stored as hashes and revocable, behind a /mars/v1 API. They’re only worth building if agents stop receiving the full session key. If that day comes, the design is in the first revision of this page.

05 / Code design

One bridge in the Canvas server, one way in.

The bridge moves entirely into the Canvas server process that fronts the page: scripts/ingress.mjs in the full stack, or scripts/static-server.mjs on its own. People and agents reach it the same way, through /mars/rpc and the /mars/sessions proxy, with the session key. The only route without the key is the OAuth callback, which has its own one-time checks.

Sign-in, step by step

  1. pagebeginSignIn({ origin }) on click. hostChecks that the callback can land (section 03), creates state and a PKCE verifier (memory, 10 minutes, single use), and returns { attemptId, authorizeUrl, mode }.
  2. pageOpens about:blank synchronously in the click handler, so popup blockers allow it, then points that window at authorizeUrl. Electron already sends such windows to the system browser; the OpenHands Cloud device login uses the same route.
  3. personPicks the team on DigitalOcean and approves.
  4. DigitalOceanGET /mars/oauth/callback?code&state on the Canvas origin. (Later, paste-back sends the same address through completeSignIn.) The route needs no cookie: it may arrive in a system browser that has none. The single-use state and the PKCE verifier protect it.
  5. hostPOST /v1/oauth/token with the code and verifier. It receives a one-hour access token, a refresh token and info.team_uuid and info.team_name. It then checks that the token can list sessions, and writes the vault before the metadata.
  6. pageawaitSignIn(attemptId), a long poll, resolves, and the panel lists the team’s agents. The callback tab says “Signed in to DigitalOcean as My Team. You can close this tab.”
Refreshing without racing yourself

Refresh tokens are single-use, and a refresh invalidates the previous access token. Two refreshes in flight would leave the host holding a dead token. So each process refreshes once per connection at a time, a lock file covers several Canvas processes sharing one keychain, and the new pair is saved before it is used.

async function accessToken(id) {
  const s = await vault.read(id);
  if (s.kind === "pat") return s.token;
  if (msLeft(s) > 60_000) return s.access_token;
  return singleFlight(id, () => withFileLock(`digitalocean-${id}`, async () => {
    const fresh = await vault.read(id);                 // another process may have refreshed
    if (msLeft(fresh) > 60_000) return fresh.access_token;
    const r = await oauth.refresh(fresh.refresh_token); // the old refresh token dies here
    if (r.error === "invalid_grant") {
      connections.setStatus(id, "needs-sign-in");      // screen E; agents get a 401 that says so
      throw new SignInRequired(id);
    }
    await vault.write(id, { ...fresh, ...r });          // persist before use; if this throws, the old
    return r.access_token;                              // token is already spent: report needs-sign-in, never success
  }));
}
Restoring a DigitalOcean backend without overwriting it

Adopted from the companion page. A persisted credential removes the most common restore failure, but not every one. Restore has to repair whichever step is missing while leaving the saved destination alone.

  • Each DigitalOcean backend record carries marsConnectionId next to marsSessionId. Reconnects use that connection, never “whichever team is active”. When an old record has no connection ID, Canvas checks which team owns the session, and asks the person if it can’t tell.
  • Root picks a DigitalOcean recovery screen for a managed DigitalOcean backend: unlock the host, sign in again (screen E), keychain locked, session unreachable, or session deleted. The generic local API-key form never edits a managed DigitalOcean record. That form is the path a maintainer flagged on #18604.
  • Restore wakes only the selected session, and it never creates a replacement because a restore failed.

The desktop app joins the host bridge

Electron stops creating its own bridge in the main process, and the preload drops window.marsBridge. Electron also stops passing marsWebBridge: false to the stack. The page then finds the bridge at /mars/health, exactly as a browser does.

Before the stack starts, a one-time migration reads mars-credentials.json (v1) from the app’s data folder. It decrypts each token with safeStorage, writes vault entries and v2 metadata, and renames the old file to .migrated. Implicit-grant tokens move as access-only connections, and they renew through the new sign-in when they expire.

The trade: DigitalOcean in the desktop app now needs the ingress process, which the stack starts after waiting for the local Agent Server. The desktop app already opens its window from that ingress, and already shows a startup failure when the Agent Server doesn’t come up. So no setup that works today loses DigitalOcean. Letting DigitalOcean work while the local Agent Server is down would be a separate improvement.

Why restarts stop breaking the cookie

The cookie value becomes HMAC-SHA256(session key, "mars-web-cookie/v1"). It stays valid across restarts and changes when the key rotates, so control-openhands restart --rotate-key still invalidates it, as it should. Nothing new is stored. The accepted cost: there is no signing out one browser; rotating the key signs out all of them.

06 / Security

What could go wrong, and what stops it.

07 / Rollout and checks

Three steps, each useful on its own.

Step 1

Stay signed in

SecretVault and ConnectionStore behind today’s browser token sign-in. The derived cookie. Team name and storage line in the panel. Desktop unchanged.

A person notices: restarting Canvas no longer signs them out, and their agents keep DigitalOcean too.

Check: the failing row from section 01 turns green. Sign in, run control-openhands restart, and the panel still lists agents; the curl from section 04 still answers. Linux CI has no Secret Service, so the run uses OH_CANVAS_SECRET_STORE=file. A Mac pass proves the Keychain path.

Step 2

People sign in with OAuth

First a small proof with a real DigitalOcean approval. Register the client (question 1), confirm the scopes, refresh once, and measure what later steps need: how long a code lives, and whether an HTTPS callback is accepted.

Then: PKCE on the Canvas origin for the desktop app and same-machine browsers; team identity; refresh and the renew banner; the plain-HTTP warning. Electron joins the host bridge, with the migration.

A person notices: “Sign in with DigitalOcean” in the browser, and no monthly re-login.

Check: a browser sign-in on loopback; a desktop sign-in after migrating an old safeStorage file; the renew banner after a refused refresh; a restart in between each.

Step 3

Agents can drive DigitalOcean

First-message auth on the proxy’s event socket; sandbox preparation on the host; the five supported calls documented and tested.

A person notices: their own agent, or one in a local conversation, can open a DigitalOcean session and work in it.

Check: from a local conversation, list agents, connect a session, start a conversation through the proxy, and stream its events with the SDK’s RemoteConversation. A session the agent itself started runs a terminal command.

Later

Each only when its proof or need arrives: paste-back for remote browsers; self-registration for HTTPS hosts; per-browser sessions, if per-browser sign-out is wanted; scoped agent keys, if agents stop receiving the full key. Also the session’s public ingress URL as a second transport, once DigitalOcean’s WebSocket fix (microvm#1920) ships.

Per AGENTS.md, feature-map and recipe updates for verify-openhands go in their own PR, after the product change.

08 / Alternatives considered

Other ways to get here.

Keep two bridges and add a keychain to the browser one

Smaller. But agents still couldn’t reach DigitalOcean through the desktop app, and the two sign-ins would keep drifting: OAuth exists in only one of them today.

Keep credentials in each browser

That puts a token-equivalent in the page, and harness-api has no CORS anyway. It also leaves agents out, and every browser signs in separately.

Scoped agent keys now

The first revision proposed them. Deferred: agents in local conversations already hold the full session key, so an extra narrow key doesn’t limit them. They become worth it only alongside withholding the full key.

Agents only ever use DigitalOcean tokens

Works from anywhere. But every agent would reimplement the port-forward tunnel and hold a team-wide credential. Kept as the path for agents far from Canvas.

A hosted token exchange with a client secret

Not needed now that DigitalOcean supports PKCE for public clients. It would add a third party that sees every user’s tokens, which is the wrong direction for an open, self-hosted tool.

Keep the implicit grant

DigitalOcean’s live metadata no longer advertises it. Its tokens can’t be refreshed, so people, and the agents using their sign-in, would lose DigitalOcean each month.

Encrypted file everywhere

One code path. But the key then sits next to the file, or in an environment variable, on every desktop. The keychain is what the OS offers for this. The file stays as the fallback for hosts without one.

10 / Open questions

Things to settle with DigitalOcean and the maintainers.

  1. One shipped OAuth client, or one per host? DigitalOcean says public clients are “typically” created through its registration endpoint, so a shipped client means OpenHands registers once that way, with loopback callbacks, and ships the client ID in config/defaults.json. That covers the first release and gives DigitalOcean one app to recognize. Registering per host only pays off for HTTPS hosts with their own callbacks, which wait for the proof anyway. Recommendation: one shipped client, with DO_OAUTH_CLIENT_ID as the override. Ask DigitalOcean whether it would rather register the client itself, and how it appears on the consent screen.
  2. Scopes and refresh-token lifetime. Does a public client get agent_harness_session:read and :operate? The reference doesn’t say how long a refresh token lives. That decides how long a host can sit idle before someone signs in again.
  3. The paste-back proof. The reference doesn’t state how long an authorization code lives, or whether it is single-use. Does the failed callback page keep its full address in iPad Safari?
  4. HTTPS callbacks for self-registered clients. Accepted for non-loopback HTTPS addresses? The reference doesn’t say.
  5. Should the bridge methods take an explicit connection? Today an agent’s connect follows the UI’s active team. An optional connectionId argument would let an agent pin its team.
