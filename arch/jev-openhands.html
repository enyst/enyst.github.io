What was released?

TypeSafe announced Jev in early access on September 15. It accepts text or structured textual state and answers typed questions without generating prose. The public model is jev-1.13.0. The three usage examples here correspond to its three primitives, Choice, Noul, and Score. See the launch announcement and primitive definitions.

PrimitiveReturned valueOpenHands use
ChoiceOne supplied option, distribution, confidenceRoute an issue or select a verification skill
NoulProbability of yes; no separate confidence fieldEvidence sufficiency; individual security concerns
ScoreExpected level on an ordered rubric, distribution, confidenceRank relevance to a reviewer’s interests

The current documentation gives 64k tokens for the whole request and 32k for state plus the longest question; Choice supports up to 255 options and Score up to ten levels. Input is text only. Pricing is $0.042 per million input tokens, with output free. Pin the model: aliases can move. Model limits and pricing; HTTP contract.

Type safety constrains the answer space; it does not establish factual correctness. The vendor documents weaknesses with indirection, arithmetic, irrelevant long context, and adversarial state. Confidence is derived from the answer distribution, not an independently verified probability that a workflow is safe. Confidence; Known limitations.

The vendor’s workflow comparisons use large-model consensus as reference labels. Treat their speed/quality comparison as vendor evidence, not measured OpenHands performance. Our measurements below use a different workload and include connection overhead. Workflow evaluation methodology.

Where to put it in OpenHands

A read-only inspection of local Canvas and Cloud definitions informed the recommendations. The existing workflow families include attention routing and notebook selection, duplicate detection, QA validation, test-quality sweeps, upstream porting, and fast security auditing. This public page describes integration opportunities; private prompts, account identifiers, endpoints, and run records are omitted.

RecommendationInsertion pointHowValidation / boundary
1 · Personal attention queueBefore the attention router or notebook research spends a full agent turn.Fetch open state and unresolved work in code; score each candidate separately for memory/context, core design, and verification. Rank, deduplicate related work, and keep a near-threshold review band. Distinguish “investigation can start” from ready-for-dev template and acceptance-criteria requirements.

The existing public Fast Audit implementation already uses direct HTTP calls, independent security estimates, bounded source context, and commit-linked evidence. Extend its rubrics rather than introducing another overlapping review publisher. The proposals on this page do not modify it.

Code decision: sdk

For production, supply the repository/component map and allow repo-local CI or documentation ownership. Our public SDK CI example was classified as Automation: “automation” as a concept is not the same as the Automation repository. No issue is relabeled or moved by this example. Fetch referenced reproducers before deciding the author supplied too little evidence. The synthetic SDK example states that a reproducer exists; the test does not execute that fictional reproducer.

Code decision: priority_verification

The paired locked recheck dropped TOCTOU from 0.76 to 0.10; the path check/open pair scored 0.83 versus 0.11 for verified-descriptor use. Remote install execution scored 0.98 while download-only scored 0.07. These obvious fixtures exercise discrimination and benign exceptions; they do not estimate detection rates for subtle real vulnerabilities.

How to verify a flagged TOCTOU: identify the checked invariant, mutator and use; introduce a controlled barrier between check and use; mutate state; compare old and fixed behavior. For cancellation, hold the resource lock, queue a tool, cancel it, release the lock, and verify that the side effect never runs. For supply-chain risk, trace trigger → checkout revision → install hooks → token permissions; inspect pinned workflow and lockfile data without executing untrusted installs. Report evidence scope and missing callers.

Code decision: shortlist

A useful failure in the policy: the core-lock case scored 1.97 with 0.94 confidence, satisfying our expected relevance range but missing the 2.0 shortlist threshold. The live public lock-fix description scored 2.01. The model checks pass while the selection policy can still miss relevant work. Keep ranked candidates and a review band instead of interpreting a tiny score difference as a meaningful distinction.

Reproduce and inspect the evidence

The study made 57 successful requests with 43,804 input tokens. Client wall time: median 735.74 ms, nearest-rank p95 894.27 ms. Estimated input cost: $0.001839768 at the documented price; this is not a billing receipt. Calls were sequential with fresh urllib connections, so this is not a pooled-connection throughput benchmark. The separate one-request authentication smoke test is excluded.

There are 21 synthetic cases (six triage, nine security, six relevance), twelve public-description cases, and 24 ambiguity probes. Expected fixture ranges were written before the calls. All 35 semantic checks passed; all 57 responses passed shape/range checks and local routing replay. Six offline regression tests cover recorded answers, malformed responses, sufficiency gating, non-approval security routing, closed-work exclusion, and the score boundary.

  • run.py — standard-library API client, validation, policy and replay.
  • cases.json — complete frozen inputs and prewritten expectations.
  • results.json — exact request/response records and client timings.
  • summary.json — check outcomes, cost estimate and case hash.
  • test_contract.py — offline policy/contract regressions.

Before enabling decisions

Label a representative OpenHands set independently, including missing references, ambiguous ownership, adversarial text, subtle races, benign installs, and multiple interests. Freeze the rubric, evaluate a fresh held-out set, measure recall and false positives per use case, and repeat near decision boundaries. Record model, rubric hash, immutable evidence revision, omissions, latency, cost, and the final verified outcome. A service error or missing evidence must produce a visible retry/review state, never a safety verdict.

The three examples are fully exercised at the API-to-local-decision boundary. Production collector completeness, account-level calibration, durable automation state, publication races, real vulnerability verification, and compaction task quality remain separate work. That boundary is the reason to start with observation and ranking.
