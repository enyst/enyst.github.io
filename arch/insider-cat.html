Agent Canvas · Apps · behavior and design

Insider Cat

A sibling of SmolPaws, living inside Agent Canvas. A companion you can talk to while it helps you find, understand, and coordinate your work.

Implementation updated 16 September 2026; provider documentation reviewed September 14–15. Worktree prototype · not released

The Cat has a durable App conversation and two voice paths in development worktrees. The standalone App lives in enyst/insider. The September 15 work added persistent Canvas controls and a public Realtime API broker. On September 16, the optional Codex Voice relay passed three real spoken request-and-answer checks across two calls, using an existing Codex sign-in and generated speech. Physical iPad microphone testing remains outstanding. These worktree changes are not presented as released or available from the repositories’ main branches.

A sibling with its own place

Insider Cat should share SmolPaws’ curiosity, warmth, directness, and habit of checking real evidence. Its home and responsibility are different: it helps the person using Canvas orient across projects, read progress, continue the right conversation, and hand work to other agents.

Sibling is the product decision. The older prompt calls it SmolPaws and assumes a local agent-server. Preserve existing tags for compatibility, but do not infer shared identity, permissions, memories, or a local backend from them. The active backend and the capabilities actually supplied by the runtime determine what the Cat can do.

Use Insider Cat for the companion and Projects for its overview. “Secretary” is the older prototype’s skin name. Projects remains the home for choosing work; the new optional companion host capability keeps the Cat’s controls available while navigating elsewhere in Canvas.

The page becomes a Canvas App

The standalone repository is enyst/insider; the original development copy remains at odie/apps/insider-cat. The standalone copy contains its own source, skill, translations, tests, and build dependencies. Its canvas-extension.json declares the Projects page, and its prepared extension.js exports activate(host). Canvas mounts it at /extensions/insider-cat/projects. The inventory is called Apps and lives at /apps; the manifest and API retain their older “canvas extensions” names.

1. Agent Server installs the package and stores its manifest, revision, bundle, and enabled state.

2. Canvas loads the enabled App and registers its Projects page.

3. The page uses the host for authenticated requests to its owning backend and navigation within Canvas.

4. Agent Server keeps the work: conversation IDs, user messages, agent events, and results remain available after leaving the page.

This replaces the skin server, iframe messaging, fixed browser ports, and page-owned credential handling. The typed App uses existing Apps and conversation endpoints. The new voice path adds conversation-scoped server endpoints and an optional persistent host surface. Apps remain trusted code running in Canvas’ browser context, so installing and enabling are separate actions.

Install on the selected backend

The instructions below install the version at the chosen source and ref. To exercise the September 15 prototype, install the prepared App from its development worktree and run the matching Odie and SDK worktrees. Installing the public main ref does not imply those unmerged changes are present.

  1. Use a Canvas build with Apps and an Agent Server with the Canvas Extensions endpoints. If Apps reports an unsupported backend, update that backend first. The inspected host currently supports local Agent Server connections, not the cloud backend.
  2. Open Customize → Apps. Set Source to github:enyst/insider, Ref to main or a reviewed commit SHA, and leave Repository path empty. For a local checkout, use its absolute directory on the Agent Server machine as Source and leave both other fields empty. A container needs its own mounted path.
  3. Review the installed App and enable it. Installation starts disabled. Open its Projects page from Canvas.
  4. Choose the real workspace for the Cat and use a configured server agent profile. The server resolves that profile’s model and credentials; the bundle contains neither.

The backend copies the prepared package; it does not run a build. Developers rebuild extension.js after editing the source, translations, or canonical Insider skill, then reinstall the updated package. The bundle includes the App’s copy from Canvas’s 15-language catalog. Keep it self-contained: the host serves the entrypoint as a browser module, without a separate static asset server.

September 15: a working development prototype

The changes are isolated on gpt/insider-ui-voice worktrees for the standalone App, Odie, and Agent Server. The browser test uses Canvas on port 8010 and its separate backend on 19000; these are test addresses, not product defaults. The App is installed through the real Apps flow.

  • One conversation across both views. The first Cat was created from Projects. A follow-up in Canvas’s regular conversation view was saved under the same ID. Opening either view does not create another Cat.
  • New means another Cat. /new from a regular Insider conversation opens a fresh App draft; the first message creates a distinct second ID. The App’s New button and /new command both navigate to the new-draft URL. Creation and picker selection then navigate to the chosen Cat’s canonical URL, so a bookmark or reload preserves the intended new/resume state.
  • Resume deliberately. The picker exposes older Cats and remembers a choice for its backend and organization. Legacy top-level conversations tagged smolpaws: insider are accepted without rewriting their saved profile or instructions. Delegated children and explicitly different roles are excluded. Cat navigation, conversation headers, and cards identify Insider conversations.
  • Keep typing while voice stays close. Cat controls live in a persistent dock below the page, reserving space so they do not cover the regular composer or Send button. The same Cat stays selected when moving between Projects and regular chat. The final browser check confirmed this placement and that long Cat IDs no longer widen the page.
  • Condense without replacing the Cat. /condense keeps the ID and event log, requires a compatible configured condenser and enough history, and does not start another agent turn or approve pending tools. Resolve active work or approval requests first. Requesting compaction from the App or updated regular Canvas view ends that Cat’s active voice call, even if compaction later fails. Click Start voice after compaction completes to load the current context.

Condensation was also verified through the regular UI. The same Cat ID remained active, a condensation summary was persisted, and the full event history retained the original user messages and final answers. The /condense command was handled as a control action and did not become another agent message. The next captured model request contained the saved summary and new question, omitted a forgotten turn, and produced the fixture’s follow-up answer in that same conversation. This checks that subsequent turns actually receive the condensed context.

The verified browser conversation flows used a scripted model fixture behind the real Agent Server. Backend authentication and the missing-key preflight were checked. An OpenAI API key was unavailable, so this is not a live OpenAI speech demonstration.

Native browser transport and playback were verified with silent media. An authorized local test used real RTCPeerConnection peers, silent AudioContext streams, and temporary interception of the test voice requests. The App’s offered SDP was used unchanged. This September 15 fixture verified browser transport and call controls; it did not test real microphone permission, speech recognition, voice activity detection, audible speech, OpenAI negotiation, or account access. The September 16 Codex live checks are a separate test record.

Silent native-browser test evidence
  • Media and controls. Both RTP directions recorded 947 packets and 32,826 bytes. Native audio playback succeeded and its time advanced past 18.7 seconds. Mute and unmute preserved the same live track. Stop speaking delivered cancel and clear messages over the native data channel and paused playback while the peer stayed connected; a later output event resumed playback.
  • Conversation continuity. Moving from Projects to regular chat preserved the same call and controller. A duplicate tool call over the data channel produced one saved user request and one function result. A typed follow-up continued the same Cat while the call remained connected.
  • Condensation and reconnection. Regular-view /condense sent call cleanup before the compaction request. A new call used the same Cat, and its next delegated request returned a response based on the saved summary over the data channel. Six events were omitted from the condensed context but remained in the full 35-event history. The final actual model request contained the exact summary and new question and omitted the forgotten requests. The fixture recorded five model requests; each delegated voice request was saved once.
  • Cleanup. Across five native calls, the App’s peer and data channel closed, its input track ended, and the correctly scoped call deletion was observed before fixture cleanup. The checks covered /new, compaction, End call, a synthetic end_voice_call, and remote data-channel closure; the latter left an actionable text fallback. Afterward, all ten fixture audio contexts were closed and the temporary browser substitutions, test harness, and request interception were removed.

Tool requests arrived as synthetic data-channel messages, and the real Agent Server used a scripted model fixture. The test did not capture a physical microphone or produce a verified spoken answer.

Development locations and voice contract

The prepared App bundle must be rebuilt and reinstalled after source changes.

Canvas adds optional host.registerCompanion({id, mount}), host.onConversationContextChangeRequested(listener), and Cat page icons. The shell owns the surface and its disposal; the App owns its call and controller binding. The context-change notification is scoped to the backend and organization and ends only the affected Cat’s call when regular-view compaction is requested. Older hosts without this notification require manually ending and restarting voice after regular-view compaction. Agent Server supplies GET /api/conversations/{id}/voice, POST /api/conversations/{id}/voice/realtime, and a controller-scoped call deletion endpoint. All use the normal backend authentication.

The voice availability response also reports run_active and execution_status from the actual agent run task. The readout requires an explicitly inactive run with status finished; a persisted finish event or detail snapshot alone is not sufficient.

Historical prototype behavior

The following describes the earlier Cat feature branch and Secretary skin. It explains what informed the conversion; these are not setup instructions for the Canvas App above.

The Cat and its two entry points

The shell mounts one voice host and shares its state with the avatars. With a skin reported installed, clicking the Cat toggles voice and the separate “+” creates a fresh text conversation. Without an installed skin, the Cat itself creates that conversation. It does not resume an existing Cat thread.

The launcher uses the current Canvas configuration and adds smolpaws: insider. For an inline OpenHands agent, it appends the Insider identity to AgentContext.system_message_suffix and supplies memory tools. It preserves existing context without creating a synthetic user message. Agent-profile launches and ACP launches do not receive this same enrichment.

The inline avatar appears in ordinary conversations too, and its pose follows the viewed agent’s execution state. Running or waiting for confirmation raises its ears; idle, finished, or paused makes it sleep. That is not necessarily the Cat controller’s workload or microphone state. Voice adds connecting/live/error state. There is one voice host per mounted app, not an enforced single call across all browser tabs.

Source: Cat components and launch enrichment.

The board is a limited snapshot of conversations

The skin renders Pending · In progress · Needs input · Done. Cards show title, execution state, optional project and model, and a shortened ID. A card click replaces the prompt draft with text naming that conversation. Its “open” link opens a new browser tab.

The server fetches only the first 60 conversations; the UI refreshes on load and by button. It does not follow every conversation live. The server retains three configured project groups and Beads-reading code, but the board flattens conversation groups into status columns. It does not render a ticket board, manage dependencies, or dispatch workers automatically.

Unknown states go to “Needs input”; errors and paused work share that column. A runtime status such as finished becomes “Done” without checking whether the user’s task succeeded. Those labels are presentation rules, not a reliable task-outcome model.

Source: board.js and server.mjs. The skin SKILL still describes project lanes and per-conversation event reads.

Voice survives navigation, but context does not follow it yet

1. Canvas Cat asks the skin server for voice configuration and an ephemeral token.

2. Browser ↔ OpenAI Realtime carries microphone and playback over WebRTC.

3. The voice model chooses a bridge:
ask_the_agent → skin server → agent completion endpoint.
control_canvas → local conversation list, navigation, or board draft.

4. The result returns to the voice model for a spoken answer.

Current implementation, not the proposed durable controller architecture.

A generic page description is included once when the data channel opens. It does not include the viewed conversation’s ID or title. Updating a React reference on navigation does not send another context event. After moving from conversation A to B, “continue this” therefore has no reliable current target.

The current controls list the first 20 conversations, request navigation by ID, and read/set/append/clear the Secretary prompt box while its iframe is open. Writing the draft does not submit it. The list follows Canvas’ active backend, while the skin’s board and delegated work use its configured server: switching backends can separate what the Cat sees from where it acts.

Stopping closes the peer connection and stops microphone tracks. However, startup can still finish after Stop because there is no cancellation guard. A late agent result can also try to write to a closed channel. Startup errors set an error state and then call cleanup that resets it to idle. These paths need lifecycle tests before voice can be considered dependable.

Source: voice hook, voice host, location description, and Canvas voice controls.

Memory exists, with a narrower boundary than the old docs suggest

The combined branch has smolpaws_memory: a durable note with revision-checked replacement and dated notes with append/read/list operations. It uses a dedicated smolpaws/memory directory under the configured persistence root, falling back to ~/.openhands. The tool checks the Insider tag. It does not establish a shared store with the WhatsApp or Slack cat, and tool gating is not filesystem isolation from an agent that already has filesystem access.

Source: memory tool and tag guard and store and revision handling.

A tag is metadata. It does not by itself load a skill, grant access, or combine histories. Keep the Cat’s controller conversation distinct from the worker the person is viewing, and store their relationship with full conversation IDs and the backend identity. Browser-local spoken history should not be promoted to authoritative instructions or a successful action record.

The experience to aim for

One default companion, one visible conversation, many explicit work targets. Resume the same controller for everyday conversation; use /new only when another Cat is wanted. Projects remains a view over existing work, with clear links to each conversation. The current voice call stays bound to its Cat while navigating. Board selection supplies the work target; opening another regular conversation alone does not update that selection or retarget work already underway.

  1. Make voice an explicit control. Clicking the Cat opens its panel; a labelled “Talk to Insider Cat” button starts the microphone. Show Connecting, Listening, Muted, Speaking, and Disconnected independently of agent execution. Keep Mute, Stop speaking, End call, and Stop task separate.
  2. Show the current target. A small chip names the selected conversation and backend. Refresh that context after navigation and before an action. If a spoken name matches several conversations, show or read a short choice rather than choosing from truncated IDs.
  3. Preserve drafts. Selecting a card attaches its full ID and title as context. It should not overwrite typed text. Reading or editing a draft is different from sending it. Navigation should reuse the current Canvas tab by default.
  4. Put needed attention first. Show “Needs your input,” “Working,” and “Recent results,” with project filters and a visible refresh time. Keep errors distinct from approval requests. Show “Run ended” unless a result establishes success; a quiet or paused agent is not necessarily blocked.
  5. Make coverage honest. Fetch additional pages or say “Showing 60 conversations.” A query for “all my active tasks” must not silently use a first page of 20. Show loading, partial results, disconnected backend, and empty project states.
  6. Make every action inspectable. Show “Sent follow-up to …” with a conversation link after acceptance; show completion only after a result. Keep a short spoken answer and the full written result together. Preserve failures and pending work after reload.
  7. Keep the companion quiet by default. No automatic greeting on each reconnection or narration of every tool step. Give a brief acknowledgment during longer work, then speak when there is a useful result or the user needs to act.

Keyboard access, readable labels, captions, transcript correction for names and paths, reduced motion, and a fully usable typed path belong in the first integrated version. The Cat’s pose and a green glow can add character; neither should be the only way to understand state.

The implemented public Realtime API path

The browser requests microphone access only after an explicit Start voice and a server availability check. Agent Server keeps the standard OpenAI API key, fixes the provider origin, and exchanges the WebRTC offer through OpenAI’s supported calls endpoint. Configure OPENAI_API_KEY in the owning backend’s Settings → Secrets, or in the server environment. The missing-key message opens Secrets. A key being configured does not prove it is valid, has model access, or has usable quota.

The Realtime model calls send_to_insider for user messages. The App sends the request to the bound Cat’s normal conversation API and waits for the backend to confirm that the entire run, including stop hooks, has settled with a finished status. It then reloads the saved answer for speech. A proposed finish event alone, a failed run, or a pending approval is not treated as a completed answer. An older broker that cannot verify completion directs the user to inspect the conversation instead. The App refuses a competing voice submission while a typed request is being sent or an approval is pending. The voice model does not run a separate worker harness. Explicit spoken hangup uses end_voice_call; a bare “stop” interrupts speech without cancelling the agent’s work.

The written record is delegated text, not a verbatim voice transcript. Requests sent to the controller and its replies are saved and visible in both conversation views. The exact audio, all voice-model wording, and a complete audio transcript are not separately persisted. This distinction matters when a spoken summary is shorter than the durable result.

Keep call lifetime separate from task lifetime

Use browser WebRTC with a trusted server establishing sessions; keep the public Realtime path’s OpenAI project key on the server. Realtime supports ephemeral client credentials, and private orchestration can use a server-side connection. The older skin’s manual subscription-token experiment is separate from the new Codex app-server integration and is not a documented production authentication contract. Realtime WebRTC · Server-side controls.

Interrupting speech should stop playback; stopping a worker requires a separate task action. For Realtime, WebRTC handles interruption-related audio truncation, and sessions have a 60-minute limit. A transcript-complete event does not prove the user heard the full answer. Persist confirmed task outcomes separately from spoken excerpts, and reconnect using the durable conversation without replaying a side effect. Realtime conversations.

Evaluate semantic_vad with patient turn timing for thoughtful coding discussions, rather than relying only on a silence threshold. Test interruptions with real microphones and background speech. OpenAI turn detection.

Decision: continue validating the opt-in Codex relay with its tested configuration, while retaining the Realtime-2.1 API-key path. Measure durable delegation, interruption recovery, wrong-target actions, missing results, and cost alongside conversational feel. The Codex live checks establish access on the tested account and three saved round trips, not universal delegation, other accounts’ access, billing terms, or physical iPad speech quality.

What to borrow from Puck; where ElevenLabs fits

Amp’s Puck documentation distinguishes conversations with the helper from work threads it creates, and uses the viewed thread/project as context. That is a useful precedent for keeping the Cat controller separate from its workers.

Amp’s 18 August “Talk to Puck” article describes Realtime-2.1 delegating to the Puck agent, then speaking a summary while the full response appears in the thread. Its examples focus on active work, requests for input, progress, and follow-ups. Insider’s prototype had the voice-to-agent bridge; the App establishes a durable typed conversation to build on.

Borrow the continuity and focus on coordination, rather than copying a persona or promising monitoring with no scheduler behind it. “Keep me updated” needs a persisted follow-up mechanism with clear conditions, not an open microphone or an in-memory loop.

ElevenLabs’ Speech Engine is a relevant future comparison: it handles speech and turn-taking while the application owns the LLM. Its integration supplies conversation context and interruption signalling. Separately, ElevenAgents exposes turn eagerness and interruption controls, including a Patient setting useful for users pausing to think.

The existing Extensions ElevenLabs entry is an API-key connector, not a live-call subsystem. There is no need to add a second provider now. Keep provider-specific session logic behind a small interface while Canvas and the SDK retain conversation identity, authorization, and work records.

A skill for the Cat doing the work

A dedicated insider-cat/SKILL.md has been added under Odie’s .agents/skills for this feature. It teaches the operational relationship: sibling identity; separate controller and selected worker; capabilities grounded in real tools; dispatch receipts distinct from completion; and spoken summaries based on inspectable results.

The skill applies when runtime context identifies an active Insider Cat session. Merely discussing cats, voice, or projects must not switch an ordinary coding agent’s role. Existing smolpaws: insider tags remain a compatibility marker, not a skill loader.

Discovery and integration contract

The repository copy is odie/.agents/skills/insider-cat/SKILL.md, with references/integration.md. The SDK accepts it as Agent Skills format, discovers it when Odie is the project, and places it in available skills. That is not automatic activation.

Project discovery depends on the conversation’s working directory and Git root. Serving Canvas from Odie does not expose this file to a controller rooted elsewhere. For reliable Cat bootstrap, package the skill into the Cat’s agent context/profile and activate it there, preserving other context. Do not globally force it into every conversation or assume the voice model has an SDK invocation tool.

The App supplies the role explicitly. Its build embeds the canonical skill body, and controller creation appends it through agent_launch_additions.system_message_suffix_append. This works with the server’s selected OpenHands profile while preserving existing context. It avoids relying on the controller’s workspace to discover the repository copy. It does not install an invoke_skill tool, add worker-management tools, or wire the old skin’s voice bridge.

Keep ownership clear: Canvas owns the panel and browser interactions; the SDK/agent-server owns conversations, execution, and backend APIs; the TypeScript client exposes typed access; Automation owns scheduled follow-ups and dispatch lifecycle; Extensions owns the normal public skill/integration catalog. The Odie-local skill is an intentional feature-development copy.

In particular, the current generic SDK client-tool executor acknowledges dispatch immediately. An agent must not interpret that acknowledgment as successful navigation or a completed operation. A real result path is required for those claims.
