Checking the Agent SDK from outside

Observed and clarified 9 October 2026 · Manual Cloud test · No active schedule

A separate verifier tests a running Agent Server through REST and WebSocket. A live subscriber can miss events. The server must let that subscriber recover durable events through replay.

Current state: The Cloud automation is registered but disabled. Its live-order check needs correction. We removed its temporary test endpoints and keys.

Why check from outside?

The testing strategy describes the larger aim. Code-writing agents can change repository tests. A trusted checker must hold the active rules and assign the result outside the candidate.

A candidate is the Agent Server build under test. A contract is the list of required behaviors. The verifier sends requests to the candidate and checks the replies.

The verifier uses public REST and WebSocket interfaces. It does not load candidate tests, plugins, helpers, or expected results. The verifier assigns each result from its own rules.

Replay contract: A live subscriber can miss events. Replay must return missing durable events in history order, including after a server restart. A live stream does not have to deliver every event.

What the manual Cloud run found

On 9 October, the verifier tested SDK commit 9f47d471. A local controller started that build in a restricted process sandbox. This manual setup did not prove that an unattended service can isolate and identify each candidate.

The first Cloud attempt found a DNS fault in that sandbox. We corrected the test setup and ran the same verifier bundle again. The second run reached the scripted provider and recorded a request witness.

Why it is disabled

Cloud runs the verifier. It does not build a pinned SDK candidate for this job. The manual candidate, provider route, and restart control used temporary services. Those services are closed.

The current Cloud definition has no active test keys. It cannot repeat this test without a new candidate, new controls, and new configuration.

The verifier runs in a Cloud context separate from agents editing the code repositories. This gives the experiment a useful boundary. A required merge gate can add stronger approval and publication controls later.

A run status is not a contract result. All required scenarios must pass in the evidence. A failed observation is a fail. A missing candidate, key, or trace is blocked.

Path to regular checks

  1. Correct the replay check

    Remove the no-gap live requirement. Test recovery from the subscriber's last saved position. Check that replay returns every missing durable event in history order, even after restart.

  2. Build a known candidate

    Choose one exact main or release commit for each run. Build its artifact and record the hash. Record which test endpoint serves it.

  3. Provide test controls

    Host the scripted provider where the candidate can reach it. Record its request witness. Add a restart control that kills the process and keeps its storage. Issue limited test keys.

  4. Run an advisory experiment

    Run the corrected verifier in Cloud. Export evidence before the sandbox ends. Check the replay trace, provider witness, and restart record. Treat missing proof as blocked.

  5. Repeat and review

    Start a regular main or release check. The proposed first cadence is daily at 09:00 in Stockholm. Review failed or blocked evidence. Retain failing storage until investigation ends. Then remove test keys and candidate resources.

Label these scheduled results experimental. They can guide repairs without blocking merges. A required pull-request check can follow when the run path is reliable.

Before that gate, independently approve the verifier bundle and configuration. Confirm the endpoint serves the exact candidate artifact. Publish the verdict from a separate identity. A new PR head or base needs a new result.

What to test next

The present bundle focuses on event transport. Later rules can cover run ownership, cancellation, confirmation, secret delivery, streaming, storage faults, and client compatibility.

Each new rule needs a clear scope. A known good case must pass. A deliberate wrong case must fail. Required gates will need a separate review path for rule changes.
