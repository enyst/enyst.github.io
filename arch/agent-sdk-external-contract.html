Why check from outside?

The testing strategy describes the larger aim. Code-writing agents can change repository tests. The contract lives in enyst/automations, outside the SDK repository. A separate Cloud automation runs the verifier.

A candidate is the Agent Server build under test. A contract is the list of required behaviors. The verifier sends requests to the candidate and checks the replies.

The verifier uses public REST and WebSocket interfaces. It does not load candidate tests, plugins, helpers, or expected results. The verifier assigns each result from its own rules.

Replay contract: A live subscriber can miss events. Replay must return missing durable events in history order, including after a server restart.

What the manual Cloud run found

On 9 October, the verifier tested SDK commit 9f47d471. A local controller started that build in a restricted process sandbox. This manual setup did not prove that an unattended service can isolate and identify each candidate.

The first Cloud attempt found a DNS fault in that sandbox. We corrected the test setup and ran the same verifier bundle again. The second run reached the scripted provider and recorded a request witness.

Why it is disabled

The first Cloud test used temporary services outside Cloud. Those services are closed. The later experiment started the pinned candidate and test fixtures in one fresh Cloud sandbox. That sandbox was removed after evidence export.

The experimental definition remains inactive. One manual pass does not prove that a daily job can select each new main or release commit, preserve failure evidence, and recover from setup faults.

The contract lives outside the SDK repository. The candidate and verifier share a sandbox in this experiment. That setup cannot protect verifier files or credentials from hostile candidate code. Use it only for advisory checks of trusted revisions. A required merge gate needs a stronger boundary.

A run status is not a contract result. All required scenarios must pass in the evidence. A failed observation is a fail. A missing candidate, key, or trace is blocked.

Path to regular checks

  1. Keep the corrected replay check

    Use the experimental bundle's replay rule for new results. Do not use the first bundle's live-order rule for a contract verdict. Record the exact bundle hash for every run.

  2. Select each new candidate

    Choose one exact main or release commit for each run. Verify its Git source archive hash in the fresh sandbox. Record the candidate's Python import paths and local port. The setup receipt is local evidence, not an attestation of installed code.

  3. Repeat the Cloud setup

    Test the native setup in more fresh sandboxes. It must start a pinned candidate, a local scripted provider, and restart control with test keys. Treat a setup fault as blocked, and retain the Cloud setup log.

  4. Keep failure evidence

    Export exact evidence before each sandbox ends. Save failing traces and needed storage for review. Check the source hash, replay trace, provider witness, and restart record. Treat missing proof as blocked.

  5. Start advisory checks

    After repeatable manual runs, enable a regular main or release check. The proposed first cadence is daily at 09:00 in Stockholm. Review failed or blocked results, then remove test resources.

Label these scheduled results experimental. They can guide repairs without blocking merges. A required pull-request check can follow when the run path is reliable.

Before that gate, run the candidate where it cannot read or change verifier files, credentials, or the result publisher's key. Independently approve the verifier bundle and configuration. Confirm that the endpoint serves the exact candidate artifact. Publish the verdict from a separate identity. A new PR head or base needs a new result.

What to test next

The present bundle focuses on event transport. Later rules can cover run ownership, cancellation, confirmation, secret delivery, streaming, storage faults, and client compatibility.

Each new rule needs a clear scope. A known good case must pass. A deliberate wrong case must fail. Required gates will need a separate review path for rule changes.
