Routing GitHub mentions to Codex and Claude draft plan

12 October 2026 · Revised 14 October and 11 November 2026 · Proposed implementation: smolpaws/apps/github

Grow the existing GitHub Worker; don't build a second one. enyst writes @smolpaws codex … or @smolpaws claude …. GitHub delivers that to SmolPaws as a notification, which the Worker already polls. One D1 ledger and the existing minute cron carry each request to a delivered reply posted as SmolPaws. Claude runs as a Claude Code scheduled task, so every request becomes a session enyst can open and continue at claude.ai/code. Codex runs through the OpenAI Agents API, and those runs do not appear in Codex web.

The SmolPaws agent asks through a direct tool that writes the same ledger row, not through a GitHub comment. A first version returns findings as comments. Code proposals come later as branches on enyst's fork.

Revised proposal. The managed routes have not been implemented or activated.

What changed in this revision

A review on 11 November kept the correctness core and questioned the shape. These changes follow from it.

  • Trigger. @codex and @claude become @smolpaws codex and @smolpaws claude. Bare handles collide with OpenAI's and Anthropic's own GitHub integrations and forced repository-wide comment polling.
  • Intake. SmolPaws's notifications find requests. Repository-wide feeds, scan cursors, overlap windows and per-surface baselines are gone.
  • Requesters. On GitHub, only enyst can ask. SmolPaws asks through its direct tool, so every SmolPaws-authored comment can be ignored on intake.
  • Claude backend. Claude Managed Agents is replaced with a Claude Code scheduled task fired through its API, so results can be opened and continued in the web app.
  • Codex backend. Stays on the OpenAI Agents API. The plan now says plainly that those runs live outside Codex web.
  • Operator states. Dispatch unknown and delivery unknown now notify enyst through SmolPaws, not only a D1 column.

Keep hosted routing inside the GitHub app

smolpaws/apps/github already contains a Cloudflare Worker, a minute cron, an ALLOWED_ACTORS allowlist, notification polling with SmolPaws's user token, a queue and GitHub replies. Ordinary SmolPaws requests go through agentServerClient.ts to the local runner. The hosted routes are selected before that dispatch and handled by their own module. GitHub Worker source, Worker configuration, and local runner adapter.

apps/github/
  src/index.ts                  Worker wiring and route selection
  src/managedAgents/
    index.ts                    accept(request), tick(), status(runId)
    intake.ts                   Notification thread scan and mention parsing
    lifecycle.ts                Dispatch, observation and publication
    ledger.ts                   D1 requests, leases and reply outbox
    providers/claudeRoutine.ts  Claude Code scheduled task fire and result callback
    providers/openaiAgents.ts   OpenAI Agents API sessions
  migrations/                   Shared durable intake and routing schema

This is a proposed layout. Keep the module free of imports from the agent server, coordinator, personal memory and local runner protocol. Pass its storage, clock, HTTP access and comment writer in explicitly. Provider-specific formats stay inside the two adapters. The SmolPaws ask_codex and ask_claude tools call accept(request) through the Worker's authenticated interface.

A recognized @smolpaws codex or @smolpaws claude command is consumed even if it is rejected; it must not also reach the local runner. A plain @smolpaws mention keeps going to SmolPaws itself.

Build the ledger once and let both paths use it. The Worker's current dedupe, wasGithubMentionEnqueued and wasNotificationEnqueued, lives in the Cloudflare Cache API, which is local to a data center and can be evicted at any time. Replace it with D1 receipts for ordinary SmolPaws mentions too, with a migration baseline so old mentions do not run again. Cache API storage properties.

Require two integration checks: hosted requests work with the local runner unavailable, and disabling hosted routes preserves ordinary SmolPaws requests. The shared Worker remains one deployment, so a release affects both paths.

The trigger is addressed to SmolPaws

Use @smolpaws codex … and @smolpaws claude …. The provider word is an argument to a mention of an account enyst controls.

@smolpaws codex review this change for cancellation and cleanup bugs
@smolpaws claude explain whether the proposed API preserves replay behavior

Bare @codex and @claude fail in three ways. @codex triggers OpenAI's Codex GitHub integration and @claude triggers Anthropic's Claude GitHub app and Action. If anyone connects either one to the target repository, a single comment would start the real product and the router, billing and posting twice. Each mention also pings whoever owns the handle. And because the mention is not addressed to an account enyst controls, finding it requires polling every comment in the repository.

A mention of @smolpaws creates a notification for SmolPaws on any repository where enyst can comment. The Worker already polls those notifications. The repository allowlist stays, starting with OpenHands/software-agent-sdk (repository ID 1043426082), but it is a policy check, not the intake mechanism. Store IDs, not names, so a rename cannot silently change which repository may receive work.

Who acts as whom

Only enyst's immutable GitHub author ID may request work through a comment. SmolPaws asks through its direct tool. Replies are posted as smolpaws, which makes the attribution obvious and lets loop prevention be a single rule: ignore comments whose author ID is SmolPaws's.

One durability owner: cron and D1

The D1 row drives a small state machine from the existing minute cron. No Workflows, no sweeper, no provider webhooks in V1. One mechanism owns the property that matters: every accepted request ends delivered or visibly failed. It is easy to inspect, to test locally and to reason about. Cron Triggers and D1.

Each tick claims due rows with expiring leases, performs bounded HTTP operations, saves progress and exits. The provider runs the agent while the controller is idle. A twenty-minute watchdog spans many ticks; the Worker never waits for a whole job inside one invocation. Cloudflare limits cron invocations to fifteen minutes; set a much smaller tick budget. Worker invocation limits.

Polling status once a minute for a twenty-minute job is a few dozen calls. That replaces public webhook endpoints, signature verification, event persistence and handling of duplicate, reordered or lost events. Webhooks can be added later if measured latency justifies them.

Backends: one you can open, one you cannot

Ease of use from the web apps matters here. Sessions created through the Claude Managed Agents API or the OpenAI Agents API do not appear in claude.ai/code or chatgpt.com/codex: there is nothing to open, inspect or tell to "now fix it". Two beta agent APIs also bring two session models, two event vocabularies, two signing schemes and two budget systems. The plan uses a web-visible backend where one exists and says so where none does.

Claude through a Claude Code scheduled task

Configure one scheduled task (formerly a routine) once: its saved prompt, an environment with network access and setup script, and enyst's fork of the target as its repository. Give it an API trigger. Each request POSTs to that task's /fire endpoint with a bearer token and the request in the optional text field. The response returns claude_code_session_id and claude_code_session_url, so every request becomes an ordinary Claude Code web session. Scheduled tasks and Trigger a routine through the API.

Fire text arrives wrapped in a <routine-fire-payload> block marked as untrusted. The saved prompt must opt in, for example "Answer the request in the routine-fire-payload block". That wrapper is useful here: the request and its thread snapshot come from GitHub, and the saved prompt stays the authority.

The fire API does not return the session's answer. The router passes a one-time result token in the fire text, and the session POSTs its findings to the Worker's /managed/results/{requestId} endpoint with that token. A missing callback is caught by the watchdog. The token can deliver one result for one request and nothing else.

Caveats. The /fire endpoint ships under the experimental-cc-routine-2026-04-01 beta header and scheduled tasks are a research preview. API fires are limited to 30 per hour per task and 100 per hour per account. Runs draw on enyst's subscription usage. Anything the session does through connected GitHub access appears as enyst, which is why the credentials section narrows it.

Codex through the OpenAI Agents API

There is no clean server-side way into Codex web. codex cloud exec creates a Codex web task but depends on ChatGPT login. That is the same dependency that stopped the OpenHands Cloud Codex ACP canary on 12 October, when it required ChatGPT reauthentication. For an unattended path, use the API-key route and accept that these runs live outside the web app.

Start with POST /v1/agents/sessions, an openai_hosted environment and a pinned model. The beta header is OpenAI-Beta: agents=v1; the key needs api.agents.read, api.agents.write and api.responses.write and stays in the Worker. OpenAI Agents API overview and quickstart. If Codex web visibility later becomes worth the authentication fragility, codex cloud exec can replace this adapter.

Neither backend reads personal chats, desktop tasks or their memory. Supply the skills and instructions each needs explicitly.

Intake from notifications

GitHub notifications describe threads, not individual comments. A thread's mention reason can persist through later activity, and the Worker today reads only latest_comment_url, so two requests in one thread between ticks would lose one. GitHub notification semantics.

Treat a notification as a pointer to a thread, then scan that thread. For each mention notification on an allowed repository, list that issue's or PR's comments, review comments and review summaries since the thread's last scan, kept per thread in D1 with a short overlap. Parse each item for @smolpaws codex and @smolpaws claude, and mark the notification read only after the rows are written. The scan stays bounded to threads that mention SmolPaws, so repository-wide cursors, overlap windows across feeds, leases on scans and activation baselines per surface are no longer needed.

Review summaries and PR or issue descriptions that mention SmolPaws also produce notifications. They come with the same scan instead of a separate later intake path. At activation, ignore items created before the activation time so old requests do not run.

Authorization and mention parsing

Authorize by enyst's immutable GitHub author ID, read from the API. A copied name, a quoted request and author_association do not authorize work. Ignore every comment authored by SmolPaws.

Parse actual mention tokens in authored Markdown, ignoring code, blockquotes and URL destinations. Match @smolpaws case-insensitively with handle boundaries, followed by codex or claude as the next word. @smolpaws-example is not a match. Two commands in one comment create one request per provider.

Freeze the request, label the context

Freeze the first qualifying observed body. Before dispatch, fetch the source again: deletion, or removal of that provider's command, cancels work that has not started. Any other edit is ignored, and the frozen request runs. Editing an accepted comment never starts another paid job; ask again in a new comment.

Put the frozen request first. Follow it with a thread snapshot in which each comment is labeled with its author and source, marked as untrusted, and capped at twenty comments and 32 KiB, with a per-comment cap so one long comment cannot crowd out the rest. Say when context was truncated. Reject requests over 16 KiB rather than silently shortening them. Other authors' text can inform the analysis but cannot change the destination, the permissions or the provider.

Let SmolPaws ask directly

Give the SmolPaws agent ask_codex and ask_claude tools, plus a status tool. They call the Worker's authenticated endpoint with a dedicated service credential; the caller cannot pick another principal through its payload. Require a stable client request ID, an allowed repository and an explicit issue or PR destination. A retry returns the same durable request. Direct requests use the same ledger, adapters, budgets and reply outbox. There is no GitHub round trip and no reason for SmolPaws to comment a request for the poller to find a minute later.

A durable request and a durable reply

For GitHub intake, the request key is repository ID + surface + comment ID + provider. For direct intake, it is the authenticated principal, client request ID and provider; a repeated ID with different content is a conflict. Put uniqueness constraints on both. Store the frozen request, policy version, target commit, provider session ID and URL, result token hash, next attempt time, lease version and publication receipt.

Admit the request and reserve its daily budget atomically, then let cron claim and advance due rows. Use conditional updates with a lease owner and version so an expired tick cannot overwrite newer progress. D1 batches are transactional, but a provider call or GitHub post remains a separate remote mutation. D1 batch transactions.

accepted → dispatching → running → result ready → publishing → delivered

Other outcomes: awaiting action · budget paused · failed · canceled
Ambiguous responses: dispatch unknown · delivery unknown

A timeout after creation is not proof that creation failed. If the provider accepted work but the response was lost, a blind retry starts another paid run. For Codex, check the Agents API's idempotency and listing support. For Claude, a lost /fire response can be reconciled only if the run is identifiable; put the request ID in the fire text and check in preflight whether the session can be found from it. When recovery cannot establish the outcome, park the request as dispatch unknown. Apply the same rule to GitHub publication.

Unknown states must reach enyst. Dispatch unknown, delivery unknown, budget pauses and watchdog expiries send a SmolPaws message to enyst with the request, thread link and session link. Known failures also get an attributed status comment on the thread. A delivery unknown row gets no further comment until its receipt is resolved.

Completion is checked against the request

For Codex, fetch session state and new events on each due tick. Idle can mean waiting for permission or input. Require the current request's answer and a compatible completion reason, and persist the event cursor and bounded result before marking it ready. OpenAI session lifecycle.

For Claude, the result arrives through the callback. Accept it only with the matching token for a row in running, store it, and let the next tick publish. A session that asks a question instead of answering appears in the result as a question, and the reply links to the session so enyst can answer there.

Use one run per request in V1, and serialize work for the same thread and provider. Continuing one session per thread is a later enhancement. With Claude, enyst can already continue any run by hand in the web app.

Publish through an outbox

Prepare the reply in D1 before calling GitHub. Its header names the provider, the configured model and the assessed commit SHA, and links the Claude Code session where one exists. That link opens only for enyst unless the session is shared. Follow with the source request, findings and actual test evidence. Write a stable hidden run marker into the comment and record its GitHub ID on success. After a lost acknowledgement, look for that marker among SmolPaws-authored comments in the fully paginated thread before another attempt. The marker exists for idempotent publication, not for loop filtering. Don't copy command tokens into replies.

Before publishing, recheck the target head. If the PR moved, say so beside the assessed SHA, or assess the new head.

Keep credentials out of the sandbox

The Worker holds SmolPaws's GitHub token, the OpenAI key and the scheduled task's bearer token as Worker secrets. None of them enter prompts, D1 payloads, logs or agent-visible files. The OpenAI sandbox gets public source as a commit-pinned archive or public clone, with explicitly configured network access. OpenAI hosted sandbox configuration.

The Claude Code session is different and needs care. Its GitHub credential never enters the VM, because a proxy attaches it on the server side. But the session can still act as enyst through that proxy and through any connectors on the task. Narrow it:

  • Attach only enyst's fork as the task's repository, and fetch the upstream as a public remote. Pushes then land on the fork, by default on claude/ branches.
  • Attach no GitHub or other write-capable connectors to the task, so the session cannot comment as enyst.
  • Allow the Worker's host in the environment's network access so the result callback works, and nothing broader than the build needs.
  • In preflight, check what the proxy allows against the target repository, where enyst has push access.

Code changes through the fork

After the comment path is proven, @smolpaws claude implement … can ask the session to push a proposal branch to enyst's fork, which Claude Code sessions do naturally. enyst opens the PR by hand at first; automated draft PRs can follow. This avoids contributor-fork permissions entirely in V1. For Codex, the router would apply a returned patch to a fork branch under a path policy, which is more work and comes after Claude.

Use ordinary comments for reviews. Formal approvals and requests for changes affect repository gates and stay a separate decision. No pushes to the target's default branch and no merges.

Bound jobs and measure cost

Intake adds little to GitHub reads. The Worker already polls notifications every minute, and the thread scan runs only for mention notifications. Read the rate headers and back off on primary or secondary limits; SmolPaws's allowance is shared with its ordinary work.

Proposed starting limits are two concurrent jobs, one per thread and provider, twenty requests per day, and a twenty-minute watchdog. Reserve the daily admission budget atomically before launch. Claude runs draw on enyst's subscription usage, and the router cannot stop one partway; treat the watchdog as a limit on waiting, not on spend. Set per-session limits for Codex from what the Agents API supports at preflight. Measure real usage on the fixture before settling the budget. Cloudflare pricing.

Roll out in three stages

  1. Ledger and intake in shadow mode. Move SmolPaws's Cache API dedupe to D1. Add notification thread scanning, parsing, the direct tool and cron progression. Prove author filtering, multiple requests per thread, missed-tick recovery, direct-call authorization and separation from the local runner. No provider calls and no new posts.
  2. Both backends on a controlled fixture. First confirm the scheduled task's API trigger and result callback end to end, then the Agents API with a pinned model. Exercise restarts, lost responses, stale heads, questions instead of answers, budget pauses and the operator messages. Require one attributed current result per successful request and a visible status for every failure.
  3. Enable the allowed repository. Set the activation time and turn on replies. Keep intake, each provider and publication independently switchable. Check that ordinary SmolPaws requests still work.

Proposal branches on the fork and session continuation per thread follow as separate work.

Decisions to make at implementation time

  • Confirm in preflight that the scheduled task's API trigger, result callback and fork-only repository behave as described.
  • Choose the Codex model, sandbox setup and per-session limits from what the Agents API offers then.
  • Decide whether Codex web visibility is worth moving to codex cloud exec once its authentication is reliable unattended.
  • Choose where operator messages land: SmolPaws's usual channel to enyst, or a pinned GitHub issue.
