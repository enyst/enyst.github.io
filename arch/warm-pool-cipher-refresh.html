Warm-pool key rotation: refresh the stores

The server accepted the right keys, but its cached persistence stores kept the startup cipher. Rebuild those stores before the initialized services use them.

OpenHands Agent Server · Fix in PR #5758 · 16 October 2026

The setup. A warm-pool server boots before it knows the user’s keys. Startup code can already create settings and secrets stores, which capture the boot cipher.

A encrypted the saved data B new user key C temporary boot key

Before · the cache keeps C

  1. POST /api/init receives B + AThe new config has both the current and previous key.
  2. Existing stores still hold CPassing the new config to a singleton getter returns the same cached store.
  3. Rotation uses the stale storesThey never receive A, so saved values remain unreadable.
  4. Init 200 · settings write 409The saved LLM key appears missing. Data on disk stays intact.

After · refresh at initialization

  1. POST /api/init receives B + AStop boot telemetry before clearing the stores it reads.
  2. Reset the cached storesClear in-memory references; preserve the saved files.
  3. Fresh stores use B + ARead with A; re-encrypt settings and secrets with B.
  4. Start consumers → readySaved credentials are available. Reads and writes succeed.

One lifecycle boundary, using the existing reset

await shutdown_telemetry_sink()
reset_stores()
await asyncio.to_thread(
    reencrypt_stale_stores, new_config
)
# Then build telemetry and services.

Order matters. New telemetry reads persisted consent; the conversation service captures its stores. Both must start after the reset and rotation.

The fix adds the existing reset and moves re-encryption earlier. See the small production diff.

Verified through startup → init → settings

Regression tests cover rotated and already-current keys. Real-process HTTP checks reproduced the failure, then confirmed working reads and writes with the fix. A restart with B alone recovered the saved values. Evidence and scope.
