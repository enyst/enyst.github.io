DigitalOcean / MARS · 19 October 2026
Proposal · no product changes yet

Keep DigitalOcean connected.

A restart should not make you enter a token again. It must not change your selected agent’s address. Use DigitalOcean sign-in, save its permission safely, and reconnect to the same session.

Recommended direction

Use OAuth with PKCE for desktop and browser Canvas. Keep a saved personal token as an advanced option. Both methods need safe storage. The browser version also needs a separate, lasting sign-in to its Canvas host.

This proposal grows out of PR #18604 and its restart question. It separates existing code, proposed code, and checks still needed. It does not claim that a complete OAuth flow was tested.

01 / Small dictionary

There are two permissions, not one.

01Canvas host

The computer that serves Canvas to your browser. It may be your Mac or a remote server.

02Bridge

Code on that computer. It calls DO and keeps the connection to your agent open.

03DO session

The running environment on DigitalOcean that contains your agent-server. MARS is the name used by this integration.

04OAuth

You approve access on DO’s own sign-in page. DO gives Canvas a token: a secret that grants limited permission.

05PKCE

A one-time proof for OAuth. The process that starts sign-in must prove it also completes sign-in. No shared app secret is needed.

06Safe storage

The operating system’s protected secret store. Keychain is the macOS version. It keeps saved tokens off ordinary settings files.

Permission A · browser only

May this browser use this Canvas host?

The host checks its own sign-in. A cookie is the browser’s saved proof. It must not grant access after expiry or sign-out.

Permission B · desktop and browser

May this host use this DO account?

DO checks an OAuth token or personal token. The bridge holds this secret. It must not send it to the agent inside the DO session.

OAuth replaces manual DO token entry.

It does not remove the need to protect a remotely reachable Canvas host. Otherwise, anyone who can reach the bridge could use its saved DO permission.

02 / Existing code

Desktop sign-in exists. Browser sign-in is disabled.

Electron today

OAuth + saved DO credential

Electron is the desktop app shell. Its main process opens DO sign-in and receives the result at a local return address. It saves the DO token with safeStorage.

Canvas calls this process through IPC: messages inside the desktop app. There is no MARS browser cookie.

Existing OAuth · Desktop storage wiring

Browser bridge today

Personal token + memory only

The Node process on the Canvas host keeps the DO token and browser-cookie token in memory. A process restart loses both. The browser can still remember the selected DO session.

The bridge returns canUseOAuth: false. Simply showing the OAuth button would not add a working browser return path.

Memory-only store, new cookie token and OAuth disabled

The current OAuth comment is out of date.

The code uses the older “implicit” method. That method returns the access token through the browser instead of a short-lived code. It says DO has no PKCE support. Current DO documentation and a read-only check of DO’s public capability document say otherwise: DO advertises authorization codes, PKCE S256, and refresh tokens.

DO OAuth documentation · DO’s live capability document · Old code assumption

This makes the preferred direction realistic. It does not prove that our DO permissions, app registration, or browser return address already work. Those need a small, explicit test.

Why PR #18604 is useful but not enough

The PR stops a ready DO backend from looking like an ordinary local server with a missing key. It does not replace the restart flow. “Backend” means a saved destination that Canvas can connect to. On an auth error, root can still show the generic key form. That form tests the Canvas origin, then merges its fields into the selected backend. The saved DO session ID can survive while its address changes. This is a code-path risk; this proposal did not run the destructive sequence.

03 / Preferred option · proposed

Approve on DO. Keep the tokens on the host.

Use the authorization-code method with PKCE. A code is a short-lived reply from DO. The host exchanges it for an access token. A refresh token lets the host renew access without asking you to sign in again.

Click “Sign in to DO”→Approve on DO→Return a code→Host checks proof→Host saves tokens
  1. Start one sign-in attempt.The host creates a random request marker and PKCE proof. Keep both in memory for this attempt. Tie the attempt to the person and browser that started it. Expire it after a short time.
  2. Open DO’s real sign-in page.Request only the permissions used by MARS. Use a registered return address. Do not put a token or private app secret in the page URL.
  3. Receive the code at the right host.Check the request marker, browser binding and return address. Accept the result once. The host sends the code and PKCE proof to DO.
  4. Check and save the permission.Verify MARS access. Save access token, refresh token, expiry, DO team and granted permissions in safe storage. Keep an existing working connection if sign-in fails.
  5. Renew access before it expires.Allow only one renewal at a time for each connection. Save the replacement token pair together. If renewal is refused, keep the selected DO session and ask for sign-in.

DO documents public clients without an app secret, one-hour access tokens, refresh-token replacement, and dynamic app registration. DO OAuth API ↗ The older implicit method is discouraged by current OAuth security guidance.

“Almost implemented” is fair for the pieces, not the full flow.

Keep the existing DO client, connection list, tunnel code and desktop storage. Replace the old OAuth exchange. Add browser return handling, refresh-token storage, and restart recovery. Do not promise this is a one-line change.

App registration: a setup choice, not a secret to ship

DO now documents public-client registration through /register. It returns an app ID and a separate secret for managing that registration. Save the management secret on the host. Do not register a new app on every restart. Reuse it while its return address remains valid.

First test whether the existing registered app can use the new flow. Otherwise, register a public client for the installation. A remote browser host needs an approved HTTPS return address. A browser on the same computer as the host may use an approved loopback return address. Desktop can use a loopback address with a free port, as documented for public clients. Exact MARS permission support and registration policy remain test gates.

04 / Same core code · different return paths

The bridge stays beside Canvas.

Choosing DO moves the agent’s work to DO. It does not move the bridge there. The bridge stays in Electron or on the computer that serves browser Canvas.

Desktop · proposed

Return to the desktop app.

Electron opens the system browser. DO returns to a loopback listener on that computer. Electron checks PKCE and saves the result. IPC remains the route from Canvas to the bridge.

Keep tokens and the temporary proof out of the Canvas UI process.

Browser · proposed

Return to the Canvas host.

The browser opens a sign-in URL supplied by its host. DO returns to that host’s HTTPS callback. Node checks PKCE and saves the result. The UI only receives success or a useful error.

On an iPad, 127.0.0.1 means the iPad. Do not reuse Electron’s callback there.

Do not make a public desktop app secret into a server secret.

Prefer a public client with PKCE for installable Canvas. A centrally operated web service can use a server-held client secret plus PKCE. Never put that secret in shipped JavaScript or a desktop binary.

Browser callback checks
  • Start sign-in only from an authenticated, same-origin POST. Bind the saved attempt to that browser session and DO connection being added.
  • Use a short-lived, HttpOnly attempt cookie with SameSite=Lax for the return from DO. The normal bridge cookie can stay Strict. Check both the attempt cookie and request marker.
  • The callback—the return address used after DO sign-in—is reachable before normal bridge-cookie checks, but it must pass its own one-time checks. Use a configured public origin and path prefix. Do not trust an arbitrary Host header.
  • Use HTTPS for remote browser access. Treat a remote HTTP-only setup as a setup error, not a reason to drop cookie protection. Keep tokens out of URLs, logs and localStorage. Remove the returned code from the address bar after exchange. Do not load third-party content on the callback page.
  • Show success only after exchange, MARS access check and safe save complete. Cancelled, expired or replayed attempts leave the old connection unchanged.

Existing shared bridge: createMarsTunnelBridge. Existing browser transport: same-origin bridge and tunnel proxy. Callback checks above are proposed.

05 / Both options need this

Save the permission. Do not save a broken connection.

OAuth and personal tokens are two ways to get DO permission. They can use the same safe store and restore code. OAuth still needs saved secrets; it does not remove storage work.

OptionWhat the user doesWhat the host saves
Preferred · OAuth + PKCEClick sign-in and approve on DO.Access token, refresh token, expiry and connection identity. Also save app-registration details where required.
Alternative · personal tokenCreate a limited DO personal token and paste it once over a protected connection.The personal token and connection identity. If it expires or is revoked, request a replacement. Do not offer silent renewal.

Use one small storage interface.

Keep platform-specific code behind SecretStore. This is a proposed name for a small wrapper around each operating system’s storage. It supplies read, write, delete and storage status. An adapter is the small part that connects this interface to the real store. The rest of the bridge must not know which operating system saves the secret.

Where the bridge runsProposed storageImportant limit
Electron · macOS / Windows / LinuxKeep Electron safeStorage and the encrypted credential file. Add refresh-token fields and safe writes.On Linux, reject the basic_text option. Check the actual storage mode, not just whether encryption is “available.”
Plain Node · macOSAdapter to macOS Keychain.Run under the correct OS user. A locked or denied Keychain is a visible state, not a reason to save plaintext.
Plain Node · WindowsAdapter to Windows Credential Manager or DPAPI-protected storage.Verify the service account, packaging and access rules. Do not assume the desktop user’s store is available.
Plain Node · Linux desktopAdapter to Secret Service, such as GNOME Keyring or KWallet.Confirm it survives reboot. A kernel-memory store does not meet the “remember me” promise.
Linux server / containerAn explicitly configured persistent secret store, or a mounted encryption key with an encrypted credential file on a persistent volume.The key must be separate from the file. With no safe store, offer an explicit “this run only” mode or stop setup. Never silently fall back.
“safeStorage on every platform” is a goal, not one import.

Electron’s safeStorage belongs to Electron. Plain Node needs its own adapter. Keep one interface and one set of tests. Do not launch Electron just to save a Node server’s secrets.

Current store: createCredentialStore. Platform limits: Electron documentation. A Node binding such as @napi-rs/keyring is a candidate, not a selected dependency. Its Linux memory fallback must not silently become our default.

Save a complete connection, not just an access token

Give each connection a stable ID and a known DO team. Save the current token pair as one protected record. Keep public labels separate from secrets. Add a saved connection ID to each managed backend so reconnect cannot use the wrong active team.

A refresh token can be used once. Run only one renewal at a time for a connection, including requests from multiple tabs. Persist the new pair before reporting success. If saving fails after DO consumed the old refresh token, show a recovery error; do not claim renewal succeeded. Tests must cover this failure.

Record the file format version. Write a new file completely, then replace the old one in one step. Restrict file access to the host’s OS user. Make migration reversible. Do not overwrite a working credential until the new one passes the DO access check. Clear cached secrets when a connection is removed.

Keep browser sign-in across a normal host restart.

Replace the one random cookie token per process with a saved, revocable browser-session store. Give each signed-in browser its own random cookie. Save only a hash of that secret, its owner and an expiry in the host’s private state directory. A hash lets the host check the cookie without saving its raw secret.

The browser sends its cookie after restart. The host checks the saved record. Restart does not log it out. Sign-out, expiry and hosting-key rotation still do.

  • Use HttpOnly, Secure and SameSite cookie settings. These block page scripts from reading the cookie, require HTTPS, and limit when another site can send it. Set Max-Age to a bounded lifetime that matches the saved expiry. Limit the cookie to the bridge path. Check that write requests and WebSocket connections come from the configured Canvas site. A WebSocket is the live connection used for conversation events.
  • Keep the existing hosting key as an initial host-unlock method if needed. Enter it in a separate “Unlock this Canvas host” screen. Do not write it into the selected DO backend.
  • Do not store the raw cookie secret in logs or the agent guest. Persist session records with private file permissions; keep the state directory on a persistent volume in containers.
  • Start with a single-owner Canvas host. Separate records by owner. Do not turn its global DO connection list into a shared multi-user service without an ownership design.

This browser-session store is separate from the DO secret store. Electron does not need it for its MARS IPC calls. Losing or locking a secret store must not erase the saved DO backend.

06 / Restore in the right order

Keep the destination. Repair the missing permission.

Read the saved backend first. If it is a managed DO session, show DO recovery. Never send it to the ordinary local-backend key form.

Keep saved DO identity→Unlock host, if needed→Load / renew DO permission→Reconnect tunnel→Check agent-server→Open same conversation
Current risk

401 → generic key form → edit backend

The error says only “not authorised.” The form can then replace the selected DO backend’s address with the Canvas origin.

Proposed rule

Identify the missing step. Keep DO selected.

Unlock the host, sign in to DO, unlock safe storage, or reconnect the tunnel. None of those actions may edit the saved DO session identity.

Illustrative recovery · no network calls
1 · KeepThe saved DO backend and conversation
2 · ShowReconnecting to your DO session…
3 · DoLoad permission, reconnect, then probe

Open the same conversation. Do not ask for a token.

The backend ID, DO session ID and DO connection ID stay unchanged.

These are proposed states. They are not recordings of live recovery. Without JavaScript, the table below provides the same rules.

Missing stepWhat the user seesWhat must stay intact
Host sign-in“Unlock this Canvas host.” Browser only.DO backend, connection, session and conversation selection.
DO permission“Sign in to DigitalOcean to reconnect.”Saved destination. Verify the returned team before reconnecting.
Safe store locked“Unlock secure storage,” with retry.All saved records. Do not treat a locked store as an empty one.
Tunnel or network“Cannot reach this DO session. Retry or manage connections.”Credentials and destination. No generic key prompt.
Session deleted“This DO session no longer exists.” Offer a different session.Do not create a replacement silently or overwrite the old record.
Reconnection can wake a paid DO session.

Keep the current intended rule: restore only the selected session. Do not wake every saved backend. Make reconnect behaviour visible and preserve the user’s pause choices. Never create a session just because restore failed.

Existing restore only considers the active backend and waits for DO sign-in: useRestoreMarsTunnels. Proposed changes add clear failure states and saved connection ownership.

Keep kind: local for current agent-server API compatibility. Add an explicit provider marker rather than infer DO from a hostname. Old records with marsSessionId remain recognised during migration. Only the managed-session reconnect code may update their derived address.

Allow a legacy guest key to remain during migration if a deployment needs it. A DO personal token and a Canvas hosting key must never become that guest key. Strip host cookies and host-key headers before proxying, as the current bridge already does.

Migrate without losing the user’s place.

  1. Protect the backend record first.Add the DO-specific recovery branch and reject generic-form writes to managed DO records. Test it independently of OAuth.
  2. Add safe storage and lasting browser sessions.Import desktop records without changing IDs. Ask before saving a web token from a session-only connection. Do not scrape secrets from browser storage.
  3. Add the new OAuth flow.Keep old personal-token connections. Old implicit OAuth connections have no refresh token; ask for sign-in once to upgrade them. Do not delete them early.
  4. Connect old DO backends to the right saved account.If an old record has no connection ID, verify which DO team owns its session. If that cannot be proved, ask the user to choose. Do not guess from the active connection.
  5. Make OAuth the normal UI.Keep personal-token entry under an advanced option until OAuth works across supported desktop and web hosts. Keep sign-out and “forget this connection” explicit.

“Unlock this host” affects browser access. “Disconnect DO” removes DO permission and closes its tunnels. Neither action deletes a paid DO session. Use a separate confirmed action for deletion.

08 / Proof before release

Test the whole return trip.

A screenshot of an open conversation is not enough. Test restart, expiry and failed sign-in while the same DO backend stays selected.

  • OAuth: real DO sign-in grants the required MARS permissions. Test desktop local return, browser HTTPS return, cancellation, wrong request marker, wrong PKCE proof and replay.
  • Remote device: start sign-in on a phone or tablet. Confirm DO returns to its Canvas host, not the device’s loopback address.
  • Storage: macOS, Windows and Linux reopen the saved connection after process restart and machine reboot. Test locked and unavailable stores. Reject insecure Linux storage.
  • Renewal: expire an access token. Renew once despite concurrent requests. Save the rotated pair. Test a crash or write failure after DO has consumed the old refresh token.
  • Recovery: attach → open empty conversation → reload → restart bridge → reconnect → same conversation. Record the flow continuously. Compare backend IDs, DO IDs and connection ID before and after.
  • Safety: no successful or failed sign-in can rewrite the selected DO backend through the generic form. Unauthenticated browsers stay blocked. Host credentials never reach the guest.
  • Costs: only the selected session may reconnect. Restore does not create a replacement or wake every saved session. No inference is needed for these tests.
  • Compatibility: ordinary local-key setup still works. Desktop still uses IPC. Existing PAT connections and old DO backend records still open or offer a clear migration step.
Decide in a small proof first

Can DO grant exactly what MARS needs?

Test public-client registration, the required DO permissions (called scopes), and one token refresh. Test the approved return addresses. The public metadata confirms capability, not our app’s full integration.

Choose before implementation

Which Node secret-store adapter ships?

Check maintained packages, licenses, platform builds, service accounts and headless Linux. Confirm real durable storage; do not accept an in-memory substitute as success.

The decision in one sentence

Prefer DO OAuth with PKCE, but fix saved permissions and safe restore for both sign-in methods. Keep the user’s DO destination intact throughout.
