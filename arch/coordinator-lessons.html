What a working coordinator would carry over to OpenHands Projects

OpenHands Projects is being designed inside a project that already works the same way: one coordinator the person talks to, and threads that do the work. On 11 November 2026, partway through a long day of it, Engel asked that coordinator what it would recommend. These are its nine answers, each set against what the Cat and its workers do today.

“Think about this feature as we are designing it here, OpenHands Projects, and think about how your threads work. And tell me if you think you have recommendations, examples, I don't know, anything you think.”

The coordinator answered from what it does every day, with that day as the evidence. Each lesson below gives that answer, then the closest counterpart on the Projects branches: software-agent-sdk #6602 at 612402d and OpenHands #19495 at 684135f. Where Projects already does the same thing, the box says so. Where it doesn't, the gap is marked.

1Make “who is speaking” structural, not prose

How the coordinator worksEvery message it receives is labelled as the person, another agent, or the system, and a message from an agent is never the person's approval. When it passes the person's decision to a thread, it attaches the person's actual message instead of paraphrasing it.
In Projects todayThe label is a sentence. Each message between conversations opens with a bracketed line, such as [Sent by …, the coordinator of your project, not by the person. It does not approve anything on the person's behalf.], and the prompt teaches the agent to read it (project_prompts.py, WHO_IS_SPEAKING). The event also records its sender. Gap: message_project_conversation takes only the Cat's own text, so the Cat can't forward the person's message verbatim. The recommendation is a way to attach it, with the label kept as a field.

2Answers flow up on their own

How the coordinator worksA thread has no reply tool and does no addressing: its replies reach the coordinator by themselves. A thread messages another thread only when one's work depends on the other's.
In Projects todayThe same. When a worker finishes a turn, its final message reaches the Cat as an [Update from …]. The worker is told “Answer in this conversation: the coordinator gets your final message.” Conversations can message each other, but the receiver is told that the sender is not notified when it answers.

3Give the Cat a cheap way to say nothing

How the coordinator worksIt hears every message in every thread, and most of its turns that day ended in deliberate silence. It speaks when a thread is waiting on the person, when something finished, or when the person asks. Without an explicit “nothing to add” exit and the guidance to use it, a coordinator echoes every update and the project chat turns to noise.
In Projects todayHalf there. Every update ends with “If nothing needs doing, end your turn”, and the prompt says “When nothing needs the person, say so in one line, or end your turn without a message.” Copies of the person's own messages to a worker reach the Cat without waking it, so it isn't tempted to forward them. Gap: there is no explicit silent exit, so staying quiet relies on the model choosing not to write.
What shape it could take. Engel asked; the coordinator answered in three pieces, most important first.
  1. Speaking is a tool call, and so is silence. The coordinator's plain text reaches no one. It reaches the person only through a post tool, and every turn must end with that or with an explicit “no reply needed” and a reason: nothing to add, not for me, or asked to be quiet. So each time a thread says something, it makes a real choice, and silence is as easy to pick as speech. For the Cat: when a worker's update wakes it, rather than the person, its turn would end with tell_person(text) or stay_quiet(reason). When the person writes to it, it answers normally. The reason costs nothing, and it makes the silences easy to audit later.
  2. The guidance lives in the tool descriptions, as it does for react. Speak when a worker is waiting on the person, when something finished or was found, or when the person asked. Stay quiet when the worker already answered the person in its own conversation, on progress chatter, and on acknowledgements. A second, smaller lever is a notify flag on speech, so only direct answers and “this needs you” alert the person.
  3. The UI folds the quiet turns. Worker updates in the Cat's conversation would show as one thin line, “4 updates, nothing for you”, that expands on click. The board already carries the state, so the chat only needs what the Cat chose to say.
A cheaper cousin: don't run the Cat at all for some updates. Routine ones would land in its context without a model call, the way the person's messages to a worker already do, and the Cat would wake only when a worker finishes, asks or fails, or the person writes. That saves a model call per update, at the cost of a rule deciding what counts as routine. The coordinator would start with the three pieces and add this if the cost shows.

4Keep the Cat thin

How the coordinator worksIt can't run code or open a repository. That felt limiting exactly once that day, and it keeps the coordinator quick and its context small. A coordinator that starts fixing things itself stops coordinating.
In Projects todayThinner than a worker, but not this thin. The project-coordinator profile has terminal, file_editor and task_tracker, plus the project tools, and no browser (project_profiles.py). The prompt asks it to route work that takes real effort, to leave the investigation to the worker, and to review with read-only steps.

5Plan for the Cat being replaced

How the coordinator worksThat morning the coordinator was swapped for a fresh one, and Engel didn't notice. Standing rules live in project memory, and the handoff carried the recent chat. Threads write to that memory too. Long projects will outlive any one context window.
In Projects todayThe memory half exists. Project memory is shared by the Cat and its workers (read_project_memory, update_project_memory), and the start of MEMORY.md is in every conversation's <PROJECT> block. Gap: there is one Cat per project, kept alive by condensation. Nothing yet hands a project to a fresh coordinator with its recent chat.

6Second-hand is not verified

How the coordinator worksIts weakest moments were reporting what it hadn't checked: a page announced as live the day before, and that day a line it had to correct. Long thread reports also reach it cut off. The Cat's updates should say whether it is relaying or has checked, and link the worker's full message.
In Projects todayThe same cut, with a pointer. An update carries at most 4,000 characters of the worker's final message, then “[... cut; read the conversation for the rest]”, and read_project_conversation reads the rest. The prompt says “A finished run is not a finished task”, and the Cat names a worker as a mention the person can open. Gap: nothing asks the Cat to say whether it relayed a claim or checked it.

7Decisions as cards

How the coordinator worksThat day's question about splitting a PR reached Engel as options, each with its consequence and one recommended, and Engel answered with one tap.
In Projects todayThe Needs you column shows a worker's ask as a sentence under its card (project-board.tsx), and the auto-resolve judge decides what lands there. Gap: the ask is prose to parse, not choices to pick from.
Being followed up. Engel pointed out that OpenHands already has the shape of this: when an agent needs a secret it wasn't given, a card asks the person for it, and the agent uses what they enter. A general “ask the user” tool, with that card as its model, is being designed in its own thread, including whether it belongs to Projects or to every conversation.

8Show who owns a branch

How the coordinator worksSeveral threads pushed to #6602 that day, and conflict markers were pushed to #6609. The coordinator should know who owns a branch before sending a second thread there.
In Projects todayGap: the board shows each worker's state and ask, but not its branch or pull request, and list_project_conversations doesn't report them either. The recommendation is to show both on the card. Workers are told to commit only on their own branch, and the Agent Server can already report a PR's state and CI (SDK #6704).

9Title by goal

How the coordinator works“Reply with OK” is a first message, not a title. The coordinator names a thread when it starts it, verb first, by what the person will come back for.
In Projects todaystart_child_conversation has an optional title, and the tool description says to use it. Gap: nothing says what makes a good one, so a worker can still end up named after its first message.

And one smaller idea: “not now” is not idle

The coordinator can set a thread aside with a reminder. A thread with nothing happening and a thread the person said to pick up on Friday are different states. Projects has Working, Needs you, Idle and Resolved, and no way yet to say “remind me later”.

A day later: what reached the coordinator, and what didn't

On 12 November 2026 Engel tested how reactions and replies reach the coordinator. Observed that day:

  1. A bare reaction doesn't wake it. Engel put a 👍 on the coordinator's nine-lessons message, and no event arrived. Asked “did you see where my thumb up was?”, it honestly hadn't.
  2. Reactions live beside the message, not in it. The history view shows them, but only when the coordinator reads the right thread. It first looked in the wrong place, the last few project chat messages. Then it found both a 👍 and a later ⚠️ once the question led it there. The gap is not the view. Nothing prompts the agent to look.
  3. A reply under an old message does arrive. It comes as an event naming the message it sits under, and saying no one else is listening there, so the answer belongs in place, not in the main chat.
  4. “Did you see this?” is plain text. The agent has to fetch context to work out what “this” is. An event that names its target spares it the search.
  5. For Projects: a reaction is its own event, naming the message. An agent can't be expected to rescan history. The SDK reactions merged in #6609 already work this way: the agent reads [The user reacted 👍 to …] with the message's text, and a reaction that arrives while tool calls are open is held until the last result is saved. The history view should show reactions too, for when the agent does look. It is the same principle as the earlier “5/5” catch: a reaction the agent never sees is not a working reaction.
  6. Two smaller ones. PR ownership works better as a table the coordinator keeps than as a rule, so Engel dropped “the opener keeps the PR” and the coordinator routes to whichever thread fits. And wording an agent reads should say “user”, as the codebase does, not “the person”.
  7. To think about: say it, but don't interrupt. Each time the coordinator posts, it chooses whether the post alerts the user's phone or just sits in the chat. It alerts only for a direct answer to what the user just asked, and for a thread waiting on the user. That is a third level between speaking and silence. For the Cat it would be one boolean, tell_user(text, notify), with those two rules in its description. Canvas would use it to choose between a notification or badge and simply adding the message to the chat. The chat keeps a full record without every line costing attention. Today OpenHands has only a sound and an emoji in the tab title. Three desktop-notification PRs are open, and #16175 is the most mature.
