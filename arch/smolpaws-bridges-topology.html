SmolPaws · how it runs now

Bridges, one server, and the last steps

The next SmolPaws is a set of standalone channel bridges attached to one TypeScript OpenHands agent-server. Any bridge can be started on its own by a LaunchAgent; it boots the server if the server is not there. This page is the current map and the remaining checklist.

1Process topology

Earlier pages disagreed about who starts whom. The Aug 30 decision said core up, bridges attach; the WhatsApp design asked for a supervision story. The implemented answer is both: the server is the always-on core, and every bridge knows how to bring it up, so starting any single bridge is enough.

RuleWhy
Any bridge can boot the server; none stops it."Start the WhatsApp bridge and it just works", also when Slack is down.
One durable SQLite store per bridge, one versioned conversation namespace per platform (whatsapp-relay:v1, slack-relay:v1, discord-relay:v1).An old EventLog can never be rediscovered and re-sent; bridges fail independently.
The server knows nothing about channels.Delivery, ordering, retries, idempotency live in the Message Relay; the server stays upstream-shaped and re-vendorable.
Every new conversation gets a real working directory and the SmolPaws identity context.Before this, paws on Slack introduced itself as a generic assistant and its terminal tool ran in a directory that did not exist.

2What the bridges share

Slack pioneered the relay shape; the loop it ran is now src/coordinator/relayRuntime.ts (RelayRuntime) and every bridge is a thin skin over it: a platform socket, a pure handler (who is allowed, what counts as addressed, how a batch becomes a prompt, which lane it belongs to), a delivery target, and an entrypoint that sets the conversation defaults.

4WhatsApp: setup that a human must do once

WhatsApp links a "device" to the phone's account; the bridge never pairs inline. On the Mac:

npm run whatsapp:auth                       # QR code in the terminal
npm run whatsapp:auth -- --phone +15551234567   # or an 8-character pairing code
# phone: Settings → Linked Devices → Link a Device
npm run bridge:launchagent:install -- whatsapp

An existing link from the legacy process is reused. Registered chats live in ~/.smolpaws/whatsapp/registered_groups.json (the legacy data/registered_groups.json is still read). Full procedure, verification, and rollback: docs/whatsapp/README.md.

5The last steps

  1. done — Slack paws on the new stack with identity and workspace.
  2. done — shared relay runtime; generic bridge launcher and LaunchAgent.
  3. done — apps/whatsapp implemented with a deterministic end-to-end proof.
  4. next — live six-point WhatsApp canary on the Mac (ledger row → intake done → conversation + finished run → delivery rows → send_attempted + message id → reply in the right chat), behind the current channel.
  5. next — stop the legacy com.smolpaws LaunchAgent, install com.smolpaws.bridge.whatsapp, keep the legacy path as rollback until it has soaked.
  6. then — scheduler inside the bridge as synthetic intakes (bead smolpaws-kxa.4); voice outbox; Discord live check; GitHub/email onto relay intake.
  7. then — retire apps/agent-server (/turns) once nothing in use talks to it.

6Keeping the engine current

Two weekly OpenHands Cloud automations now walk the transpiles forward: one advances enyst/openhands-agent one upstream release interval per PR (runbook docs/DRIFT_AUTOMATION.md), the other re-vendors that SDK into packages/openhands-agent-server, reviews the server-side units, and regenerates the Python OpenAPI oracle (runbook packages/openhands-agent-server/docs/REVENDOR_AUTOMATION.md). Both open PRs for a human to merge. The constitution is unchanged: Maintaining the OpenHands TypeScript transpiles.
