02 / The chosen proposal · not shipped by this page

The service creates. The runner attaches.

Keep backend-specific launch knowledge in the automation service’s existing per-mode backends. Create the conversation once the run’s sandbox is ready. Pass its ID to the runner only after checking the launched profile.

  1. Service dispatches the saved profile.Wait for the sandbox to be ready.
  2. Ask the profile owner.Local agent-server, or enterprise using the run’s owned sandbox.
  3. Check launched identity.Mismatch → fail visibly before runner execution.
  4. Runner attaches by conversation ID.Send the event-context prompt, wait, report completion.
At automation creation · proposed

Save the user’s choice.

POST /v1/plugin-spec accepts an optional profile ID. Validate it against the manifest’s exact allowlists. Without an explicit choice, use the manifest’s default_name.

Canvas defaults its picker to the user’s active profile at creation. Later active-profile changes do not silently switch this automation.

At dispatch · proposed

Resolve, check, hand off.

Re-check the stored profile against the allowlists. Launch via the owning backend. On enterprise, poll the start task for the conversation ID. Verify launched_agent_profile identifies the requested profile.

Pass AUTOMATION_CONVERSATION_ID; the runner uses RemoteConversation.attach(…). Follow-up runs reuse the subject conversation when it exists.

A typed prompt becomes a plugin-spec automation too.

A stock conversation plugin receives the per-automation prompt through configuration. Canvas needs a plugin-spec create flow and profile picker. Legacy preset endpoints remain frozen and continue rejecting agent_profile_id.

Proposal, API fields, follow-up reuse and prompt options: #600 · Proposed solution / Design. Launch work: #601. Launch experience: #609.

04 / The important catch

Correct identity is only the first check.

Enterprise can stamp the right profile while constructing a different effective agent. According to #600’s source audit, its current path replaces the profile’s tools with defaults, drops its prompt suffix, and does not apply secret_refs.

Check one · provenance

“Did we launch the requested profile?”

Compare launched-profile identity with the requested ID. This detects a wrong profile or the reported fallback to composed settings.

Mismatch → stop before the runner starts.

Check two · effective configuration

“Did that profile actually constrain the agent?”

Verify the model receives exactly the allowed tools and the intended secret scope. A correct ID tag cannot establish either.

Right ID + wrong tools is still a failed rollout.

OHE rollout waits for enterprise #763.

The manifest’s “all and only these tools / secrets” promise cannot hold while enterprise replaces tools and ignores secret references. #600 treats #763 as a hard dependency. The unknown-profile fallback (#759) and worker secret boundary (#854) also need explicit attention.

These enterprise details are publicly described in #600 · Verified contracts / Known OHE limitations. Linked enterprise issues may require repository access. This page adds no private enterprise source excerpts.

Another distinction: saving a profile ID does not freeze its contents forever. The definition can be edited. Dispatch revalidation and recorded launch revision help explain what a later run actually used; immutable profile snapshots are not a stated requirement of this proposal.

05 / The design decision

Why create at dispatch?

The current plugin-spec runner prepares nothing before creating the conversation. The service already knows the mode, sandbox and user identity. Moving creation there puts failures before runner execution without adding a runner-to-service launch endpoint.

OptionAttractive because…Trade-off / current decision
Chosen: service creates at dispatchOne backend-specific launch boundary; runner only attaches.Requires a new backend method and provenance check. Keeps existing runner reporting.
A · Repair presetsFixes today’s prompt UI path sooner.Invests in a path being frozen; also needs finish-policy contracts that plugin specs do not need.
B · Runner requests creation from serviceAllows workspace preparation first.There is no such preparation today. An extra endpoint and round trip buy little.
C · Runner calls the profile ownerAvoids changing service-side launch.Duplicates local/cloud API knowledge in runners; uses the user key from the sandbox.
D · Service drives everything; no runnerAvoids per-run SDK installation.Completion, watchdog and progress currently assume a sandbox process. Possible later simplification.
Still an implementation choice

Where does the stock prompt plugin live?

Either an extensions plugin with arguments rendered from config, or a built-in plugin shipped with the automation service. Both preserve the chosen plugin-spec path.

Explicitly parked

Structured finish and model override.

The plugin-spec runner has no finish hook. Structured TaskOutcome and an independent LLM override are outside this change. The agent profile owns the model.

Why older comments seem to disagree

#600 evolved through four designs: service-driven API execution → runner calls the owner → runner requests creation from the service → service creates at dispatch for plugin specs. The fourth design is the current issue body. The run-conversation endpoint in older discussion is alternative B, not another step in the chosen design.

What would count as done?

  • Identity: local and OHE runs record the requested launched profile; mismatch visibly fails before runner execution.
  • Capabilities: record the actual tools sent to the model, including delegation when selected; OHE gets exactly the allowed tools and intended secret scope.
  • Selection: accept a profile within the manifest allowlists; reject one outside them.
  • User flow: typing a prompt creates a plugin-spec automation on the chosen profile; the runner attaches rather than creates.
  • Delivery: release automation, deploy to SaaS/Beta and bump the OHE chart. A green source test alone is not deployment proof.
A useful review question

Can a run show both which profile revision launched and which capabilities the model actually received? Keep those as separate pieces of evidence. That catches both the wrong-owner bug and the right-tag/wrong-agent bug.
