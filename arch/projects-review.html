OpenHands Projects: where it stands and what to do next

For Engel. Covers Agent Server PR #6602 at 9fb9184, Canvas PR #19495 at 53124e9, and Insider main at 0025493. I read the code at those commits and checked the notes against it. Each finding says whether I verified it in code or am inferring it.

Verdict Agent Server Canvas Insider Cross-cutting Decisions Verification gaps Path to merge Status Plan

Verdict

The server design is sound and the careful parts are careful. A Project record plus tag membership, a coordinator with typed tools, and workers as normal conversations is the right shape, and it belongs in the Agent Server. The run-lock confirmation guard, the artifact path handling, the revisioned memory and the corrupted-file handling are well made and well tested. The 170 tests in the six focused suites pass on the PR head here.

It is not ready to merge, and the reasons are mostly about the loop and the packaging, not the idea. The coordinator only hears about workers that finish cleanly, so the conversation the person relies on is blind to exactly the workers that need them. The wake-up path keeps its state in memory and drops failures. The confirmation guard covers one state, and a coordinator message still resumes work the person paused. On the Canvas side, the head commit that contains the Projects view has not been through the test workflow, and the PR carries four features under an Insider title.

The largest risk to "doing this to the end" is the one-big-PR rule. It served testing well. As a merge vehicle it means a 10,700-line server PR and a 6,900-line Canvas PR, each approved only by the review bot and each changed substantially since that approval. I recommend keeping the big branches for integration and merging through five or six smaller PRs in a fixed order, which the plan at the end lays out.

Agent Server

Paths are relative to openhands-agent-server/openhands/agent_server/ unless they start with another package name.

High

S1The coordinator is only told about runs that finish

The outcome subscriber acts on one transition: execution status becoming finished (project_board.py:149-158, :244). A worker that ends in error, gets stuck, pauses, or stops for the person's confirmation produces no update at all. The board puts those in Needs you, but the coordinator learns nothing until it happens to call list_project_conversations.

This matters more than its size suggests. The promise of Projects is that the person talks to one conversation and it surfaces what needs them. Today that conversation knows about the workers that are fine and not about the ones that are blocked.

Suggested fix. For a turn the coordinator started, deliver an update on every terminal transition, with a header that names the state ("stopped for your approval of …", "failed with …"). Add a test per state and an F36 recipe for a worker that stops on a confirmation.

Verified in code. No test or F36 recipe covers a non-finished ending.

High

S2Wake-ups depend on in-memory state and are dropped on failure

Who started the current turn, whether the agent asked a question, and the last agent text all live on the subscriber object (project_board.py:176-192). Deliveries are unsupervised asyncio tasks; an exception is logged and the update is gone (:329-344). When no run slot is free, the update is saved in the coordinator but nothing ever runs it (project_wake.py:136-139).

After a server restart the subscriber starts empty, so a worker that resumes and finishes a coordinator-started turn has _turn_sender = None, is treated as a turn the person started, and is copied to the coordinator without waking it. A long-lived project will hit a restart.

Suggested fix. At finish time, read the turn's starter from the event log (the last user MessageEvent on the active branch already records sender) instead of from memory. Make delivery retryable: on startup and on run-slot release, reconcile "members that finished after the coordinator's last update from them".

Verified by reading. I did not reproduce the restart case. F36.persist-restart checks that records survive, not that the loop does.

High

S3The confirmation guard covers one state; a coordinator message resumes paused work

refuse_pending_confirmation refuses only when the status is exactly waiting_for_confirmation (event_service.py:1653-1660). A paused, errored or stuck conversation is run. The F36 notes say so plainly: "A paused conversation is resumed." And the agent's step begins by executing any unmatched actions, which the code itself calls implicit confirmation (openhands-sdk/…/agent/agent.py:757-766).

So a worker the person stopped is restarted by the coordinator's next follow-up, and any actions left over from an interrupted batch run first. The same applies in the other direction: a worker's update wakes a coordinator the person paused (project_wake.py:125-132). The board calls all of these states "needs you"; the message path treats them as "go ahead". The Voice work reached a stricter rule for the same hazard (send_message_if_idle in #5180 refuses paused-with-pending-actions and goal loops), so there are now two guards with different answers.

Suggested fix. One shared admission check for every sender that is not the person: run only from idle or finished; for anything the board would call needs you, save or refuse and tell the caller why. Use it for the tool, the wake-up and Voice.

Verified in code and in the F36 gotchas. I did not build a paused-with-unmatched-actions reproduction; the worst case (leftover actions executing) is inferred from the two code paths.

Medium

S4The guard and project scoping are conventions, not boundaries

The tools authenticate with the server's own session key read from the environment (openhands-tools/…/child_conversation/impl.py:33-66). sender_conversation_id is whatever the caller says it is (event_router.py:280-292), and a sender that is in no project may message into any project (project_wake.py:82-89). An agent with a terminal can post to /events with run: true and neither flag; Insider's skill tells the Cat to use the API from its terminal.

For a single-user local server this is acceptable. It should be described that way. The PR text and the bot reviews call it "project isolation", and an upstream reviewer will reasonably read that as a security property.

Suggested fix. State in the PR and the route docs that these are guard rails for well-behaved tools. If real scoping is wanted later, it needs per-conversation credentials, which is a separate design.

Partly inferred. I did not confirm that a worker's terminal inherits the session key variable.

Medium

S5The Cat persona ships in the upstream tool prompt

COORDINATOR_PROMPT_GUIDANCE opens with "the cat who presides over a herd of worker conversations" and gives it "a dry, good-natured cat" voice (openhands-tools/…/project/definition.py:76-80). Every coordinator gets this, including the plain one Canvas starts. Issue #19575 asks for a coordinator "with no persona", and the decision is that the Cat is an optional layer.

The same block describes UI that may not exist ("a resolved conversation shows a banner", memory "shows in the project view"; Canvas has no memory view).

Suggested fix. Keep routing, what-you-hear and safety in the tool guidance, in neutral words. Move the voice into Insider's <INSIDER_CONTROLLER> launch addition, which already exists.

Verified in code.

Medium

S6Board state lives in user-visible tags that clients replace wholesale

project, turn, ask and resolved are ordinary tags with generic names (openhands-sdk/…/conversation/types.py:24-45). The server serializes its own single-tag writes, and its docstring admits the limit: "a concurrent PATCH of the full set still replaces it" (conversation_service.py:2117-2120). Both UIs resolve a card by reading all tags in the browser and writing all of them back (Canvas project-board.tsx:52-66; Insider src/attention.js:24-29). A resolve that overlaps a worker finishing can erase turn and ask, or restore stale ones.

The tags also leak into the product: the Canvas screenshots show "Ask: Question: for…" and "Turn: answered" as tag chips in the conversation list, and a 200-character sentence is being stored as a tag value. A person who already uses a project tag of their own will collide with membership.

Suggested fix. Add single-purpose routes (POST …/conversations/{id}/resolve and /reopen) backed by set_conversation_tag, and have both UIs use them. Reserve the four keys so the generic tag PATCH and the tag editors cannot change or show them. Membership by tag is fine for now; ask in particular would sit better in a small server-owned record.

Verified in code and screenshots. The race is by inspection, not reproduced.

Medium

S7Every message and reply in every worker is appended to the coordinator's history

The person's messages in a worker, and the worker's final reply to each, are saved into the coordinator as user-role messages of up to 4,000 characters (project_wake.py:142-222, project_prompts.py:147). In a project where the person works directly with three workers, most of the coordinator's context becomes copies it is told to ignore. That brings condensation sooner, and the known post-condensation confusion (person's words versus another conversation's) applies to the coordinator too, because these are user-role messages distinguished only by a bracketed first line.

Suggested fix. Keep the person's words, drop or shorten the reply copies (a one-line "replied; N characters, ended with a question" plus read_project_conversation is enough). Longer term, store awareness notes as a non-LLM event and render one digest into the coordinator's next turn.

Verified in code. The cost is an inference; nobody has measured coordinator context growth over a long project.

Medium

S8With the flag off, project tools are kept but every call fails

All /api/projects routes answer 404 the moment the flag is off (projects_router.py:89-103), and all six project tools go through those routes (openhands-tools/…/project/impl.py:116, :212, :313, :428). So an existing coordinator keeps its tools and its <PROJECT_COORDINATOR> prompt, and each call returns "Projects are turned off". For reactions the decision holds as stated, because the agent's tool writes the event directly.

Also, there is no mentions flag: the registry has two keys (experimental_features.py:35) and mention links are emitted whenever Projects is on.

Suggested fix. Decide which is meant. Either the flag gates creation and new conversations only (let member-facing routes keep working for existing projects), or off means off and the decision text and PR description say so. I would pick the first; it matches the reactions rule.

Verified in code. test_projects_feature_flag.py tests the 404 and the withheld tools, not an existing coordinator after the switch.

Medium

S9A worker's own child is told the wrong thing and nobody hears back from it

Any project member's child gets worker_guidance naming its parent as "the project's coordinator, the conversation that started you" and promising "the coordinator relays" its final message (conversation_service.py:2385-2395, :2566-2570; project_prompts.py:71-101). But updates are delivered only for turns the real coordinator started (project_wake.py:170-171). A grandchild's report reaches no one.

Suggested fix. Wake the conversation that started the turn, whoever it is, and word the guidance as "the conversation that started you". Or withhold start_child_conversation from workers until this is designed.

Verified in code.

Insider

High

I1Following the setup guide probably gives a Cat without coordinator tools

Insider creates the Cat from the person's active agent profile and then registers it with coordinator_conversation_id (src/extension.js:1694-1720, :1937-1940). The server adds the coordinator tools only on its own creation path, start_project_coordinator (conversation_service.py:2472-2481); making an existing conversation the coordinator only tags it. The project tools are marked not user-selectable (project/definition.py:136), so a profile made in the UI cannot include them.

The demos worked because Coordinator and Worker profiles were created by hand through the API. docs/try-projects-locally.md has no such step. Without it the Cat falls back to its skill and the API from a terminal, and workers started that way are not children, so they get no project tag, no worker profile, no memory, and send no updates. The first live run, where the Cat did all three tasks itself, looks like this.

Suggested fix. One creation path. Let POST /api/projects with coordinator: {…} accept launch additions, and have Insider use it, passing its <INSIDER_CONTROLLER> block. Then the Cat gets the tools from the server, and the two-step "create Cat, then create project" flow with its failure cases goes away.

Inferred from three code paths. I did not run the guide. This is the first thing to confirm by running it on a clean machine.

Medium

I2Insider computes its own board, with different rules

Insider pages through every conversation on the server (src/extension.js:1046-1064) and groups them itself (src/attention.js:53-66). Its rule puts any non-running conversation with turn=asked in Needs you; the server only does so for a finished one (projects_router.py:403-417). Canvas uses the server's attention. So the same project can show different groups in the two UIs, and there are three places to change when the rules change.

Suggested fix. When the Cat has a project, read GET /api/projects/{id}/conversations and use its attention. Keep the tag path only for servers without Projects, or drop it.

Medium

X3The message-origin problem needs a structural answer

The known issue (after condensation a worker can mistake the coordinator's note for the person's words) is handled today by three pieces of prose: the header line, a paragraph in worker guidance, and a sentence in the condenser prompt. All coordinator and relay messages are stored as user-role messages whose first content block is the header. The structured fact, MessageEvent.sender, is not used when the event is turned into a prompt.

Suggested fix. Generate the origin line from sender at prompt-building time, so it cannot be separated from the message, and have the condenser receive each message's origin as data. Then the stored content is just the text, UIs stop parsing prose, and S7's digest becomes easy.

Verification gaps

What is claimed or implied but not shown, and what the verify skills do not reach.

  • Blocked workers. No test or recipe for a coordinator-started worker that ends in error, stuck, paused or waiting for confirmation (S1).
  • Restart during a project. Only record survival is checked, not that a worker finishing after a restart wakes the coordinator (S2).
  • Paused targets. The behavior is documented as a gotcha, not tested as a safety property (S3).
  • Flag off with a live project. Tests cover the 404 and withheld tools on new conversations, not an existing coordinator after the switch (S8).
  • Server-started coordinator and worker profiles. Unit tests exist; I found no F36 recipe for coordinator: {…} or worker_agent_profile_id, the two paths the Canvas view depends on.
  • Long projects. Nothing exercises a coordinator through condensation with awareness copies in its history (S7, X3).
  • Canvas view. One live run; four unit tests; no mock mode; no verify-openhands family; never built by CI (C1, C5).
  • The setup guide. No record of anyone following docs/try-projects-locally.md from a clean machine with default profiles (I1).
  • Lost-message fix. The fallback path was not hit in the "after" run (C7).
  • Second model. All live evidence is DeepSeek (X2).
  • Docker runtime and Cloud. Out of scope by construction, but not stated in the server PR.

What I could not verify myself: the cause of the red tools-tests job (the log tail available to me held only cleanup lines), whether a worker's terminal can read the session key (S4), and anything that needs a running stack. I ran only the six focused server suites.
