Agent Canvas LLM Profiles design note

Notes for OpenHands/agent-canvas#533. Prepared by OpenHands (AI) on behalf of the user, June 2026.

Short version: local and remote agent-server backends already share one LLM profile model. OpenHands Cloud still exposes raw LLM settings, so the product model is not fully unified yet.

Agent Canvas LLM profiles agent-server Cloud settings /model

Current shape

Local agent-server

Uses saved profiles through the SDK ProfilesClient. The settings page is profile-oriented and conversation start consumes the active profile after the server materializes it into agent_settings.llm.

Remote agent-server

Same as local. In Agent Canvas, a remote agent-server is still a kind: "local" backend because it speaks the same agent-server protocol.

OpenHands Cloud

Still uses raw Cloud settings from /api/v1/settings. The frontend derives agent_settings.llm only so the existing raw LLM form can render.

Remaining split

Routes, navigation copy, chat labels, /model, and switch behavior still branch on backend.kind.

The useful seam

The clean boundary is the effective LLM config, not the profile name. A profile, raw Cloud setting, or future Cloud profile should all resolve to the same runtime shape before conversation start or model switch:

agent_settings: {
  llm: {
    model: "openhands/minimax-m2.7",
    api_key: "...encrypted or server-held...",
    base_url: "...optional...",
    stream: true
  }
}

That lets conversation runtime code stay mostly backend-agnostic. The backend-specific work should remain at the storage and materialization boundary.

Code shape today

AreaCurrent design
Profile lifecycleProfilesService wraps SDK ProfilesClient calls for list/get/save/activate on agent-server backends.
Conversation startAgent-server start fetches encrypted settings, then builds the runtime payload from agent_settings.llm.
Cloud settingsCloud response stays mostly flat, then derives agent_settings.llm for the raw settings form.
SwitchingAgent-server profile switch fetches encrypted profile config and calls ConversationClient.switchLLM. Cloud profile switching is not implemented.
UI copyLocal says “LLM Profiles”; Cloud still says “LLM Settings”.

What I would clean up next

  1. Centralize the capability check as something like supportsLlmProfiles(backend) instead of repeating backend.kind checks.
  2. Choose the Cloud profile storage owner before changing the UX: app/backend-owned storage is safer than browser localStorage for anything secret-bearing.
  3. Define switch semantics once: local has “activate for future conversations” on home and “switch current conversation” in chat.
  4. Keep agent_settings.llm as the common materialization seam so SaaS/local branches do not leak into runtime code.

Tiny cleanup already made in Agent Canvas: useLlmProfiles() now disables itself by default while Cloud is active, avoiding a local-only profile request in Cloud mode.
