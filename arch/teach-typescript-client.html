The typescript-client repo, and the proposal to fold it into the SDK

Someone proposed moving OpenHands/typescript-client into OpenHands/software-agent-sdk to ease releases. To have an opinion, you need to know what the client is, who depends on it, and what "the release process" actually is. This page teaches all three, then quizzes you.

★ The one thing to remember: @openhands/typescript-client is the browser-side SDK that lets a web UI drive the OpenHands agent-server over HTTP/WebSocket. Its one real consumer is agent-canvas (plus vulnerability-fixer via a git dep). It mirrors the Python SDK's API, so the two must be released in lockstep — which is the whole motivation for the move.

1Background

Deep background for beginners — skip if you know what an "agent server" and an "SDK client" are

Safe to skip if OpenHands' client/server split is already familiar.

An agent here is an LLM in a loop: it reads a task, calls tools (run a bash command, edit a file, browse), reads the results, and repeats. In OpenHands that loop runs inside an agent-server — a backend process that owns a conversation, executes the tools in a sandbox/workspace, and streams back events.

A client SDK is a library that talks to that server so you don't hand-write HTTP calls. It wraps "create a conversation", "send this message", "run this bash command", "list the files" into typed function calls. OpenHands' primary SDK is in Python (software-agent-sdk). The typescript-client is the same idea for JavaScript/TypeScript callers — importantly, ones running in a browser.

The narrow background: what this repo is

The package is @openhands/typescript-client, described in its own manifest as the "TypeScript client for OpenHands Agent Server." typescript-client/package.json Its README says it plainly: it "mirrors the structure and functionality of the Python OpenHands Software Agent SDK, but only supports remote conversations."

Two properties matter for everything below:

  • It mirrors the Python SDK. Same shapes — Conversation, Agent, Workspace, ConversationManager, ServerClient, BashClient, HttpError. When the Python SDK / agent-server API changes, the TS client has to change to match.
  • It is browser-compatible by design. File operations use Blob, File, FormData — browser-native APIs, no Node fs. That is the reason it exists as a separate TS package instead of "just call the Python SDK": a React app in the browser can't import Python, but it can import this and talk to the server directly.

It is published to GitHub Packages (the npm registry at npm.pkg.github.com), and it is still labelled ALPHA in its own README.

ⓘ "Remote conversations only" means the client never runs the agent loop itself — it always points at an already-running agent-server. So it's a thin, typed, browser-safe wrapper over that server's API surface, not an agent runtime.

2The intuition: two SDKs for one server, kept in sync by hand

Picture the agent-server as a socket in the wall. The Python SDK is one plug; the TypeScript client is a second plug shaped for a different device (the browser). Both plugs have to match the socket. When the socket's shape changes — a new field on an event, a renamed endpoint — both plugs need re-cutting, or the mismatched one stops fitting.

Right now those two plugs live in two different repos with two different release buttons. Every time the API moves, someone bumps and releases the Python SDK, then separately tags and releases the TS client. Two-repo lockstep done by hand is exactly the kind of coordination that quietly rots — you ship the server change, forget the client tag, and canvas is suddenly a version behind.

3Who actually uses it (checked, not guessed)

The proposal's risk is entirely "who breaks if the package's home or versioning changes?" So the real question is the dependency graph. Across the local clones and an OpenHands-org code search:

ⓘ So the answer to "agent-canvas? automation? odie?" is: agent-canvas, yes and heavily; automation and odie, no. Plus vulnerability-fixer via git. That small blast radius is good news for the move — but the two consumers depend on it in different ways (a pinned registry version vs a git URL), so both mechanisms have to keep working.

4The proposed move — and the one thing that can break

Today typescript-client releases on its own: pushing a v* tag runs release.yml, which builds and publishes to GitHub Packages. release.yml The Python SDK repo, meanwhile, publishes Python to PyPI and some binaries — it has no TS/npm publish step today.

"Ease the release process" means: put the TS client inside the SDK repo so one release cuts both the Python SDK and the matching TS client together — no more two-repo hand-coordination. The mirroring relationship becomes a same-repo invariant instead of a promise.

⚠ The gotcha: versioning is already out of sync. The repo's own package.json says version 0.1.1 and its newest git tag is v0.6.0 — but agent-canvas pins 1.28.0. Those are three different numbering worlds. Whatever the move does, the SDK-repo release must keep publishing @openhands/typescript-client to GitHub Packages at a version the consumers can still resolve — the pinned 1.28.0 in canvas and the git+https URL in vulnerability-fixer. If the package name, registry, or version scheme shifts silently, one or both consumers break at install time.

None of that is a reason not to do it. It's the checklist for doing it safely: keep the package name, keep publishing to GitHub Packages, and decide the version story (does it now share the SDK's version, and if so, how do existing 1.28.0 pins migrate?).
