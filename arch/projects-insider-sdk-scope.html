How Projects work

A coordinator keeps track of the whole project. Workers do the individual pieces. Each is a saved OpenHands conversation, with its own agent, tools, and history.

This page follows their work, then shows what it adds to the SDK repository. It is for reviewing the design and its scope before reading the full diff. Reactions and Insider Voice are separate additions, described below.

Work in progress. Projects is draft SDK #6602. This page describes the pinned source snapshots, not a released API or a new runtime test. It will be updated as the implementation changes. The live scenarios show the user experience; this page explains the machinery.

Two agents, two jobs

A · Coordinator

Keeps the whole picture

The person gives it a goal. It breaks the work into briefs, starts workers, follows their progress, and brings back results or questions.

Its prompt emphasizes coordination. Its default profile has terminal, file editor, task tracker, and server-added project tools. It can inspect a file without becoming the worker for every task.

One conversation is recorded as the project's coordinator. The Cat persona is optional; the coordinating role is not tied to that persona.

B · Worker

Owns one piece of work

It receives a brief from the coordinator and runs as a normal coding agent. It uses tools, changes files, tests its work, and ends its turn with a report.

Its prompt explains who sent the brief and who will receive the report. The person can also open this conversation and speak to it directly.

Workers have separate histories. They do not inherit the coordinator's chat, and their default profile cannot start more workers.

What changes in agent configuration?

The server seeds editable project-coordinator and project-worker profiles from the active OpenHands profile. It does not overwrite existing ones. The worker keeps the base tools except start_child_conversation; the coordinator gets its smaller tool set.

The SDK gains project_coordinator and project_worker prompt presets and a prompt_preset configuration field. The server assigns the role through launch additions even when a different profile is selected. A dynamic <PROJECT> block supplies the project goal, coordinator, and memory index. Under the coordinator preset, a persona replaces the soul section, not the coordinating job.

Project children use the selected worker profile rather than cloning the parent's agent. They retain the parent link, workspace/worktree behavior, confirmation policy, plugins, hooks, and secrets. They do not inherit the parent's client tools, launch additions, or app identity tags. Only project membership carries over. Non-project child launches retain their existing behavior.

Source: profiles, role prompts, launches. The earlier prompt proposal explains the motivation; the pinned code defines this snapshot.

A project in motion

  1. Create a place for the work

    The server saves a project name, description, coordinator ID, and optional worker-profile ID. Membership is a project tag on each conversation. A new project can create an idle coordinator or attach an existing conversation.

    SDK need: project storage and REST resources. Creating the coordinator does not itself send the goal or start a turn.

  2. The coordinator sends a brief

    It uses the existing start_child_conversation tool. The server launches a worker from the project's worker profile. The brief is a normal saved user-role message, with a sender ID and a header saying it came from the coordinator, not the person.

    SDK need: role-aware launch and sender identity. A new agent-to-agent message event type is not needed.

  3. The worker does the task

    It runs the ordinary agent loop: messages, tool actions, observations, and a final report. It can use shared project artifacts and memory. The coordinator can list conversations, read recent messages, or send a follow-up.

    SDK need: project tools around existing conversations. Reading a worker is explicit; its full history is not copied into the coordinator.

  4. The server delivers the report

    For a coordinator-started turn, the server appends the worker's final report to the coordinator as a user-role message and requests a guarded run. The coordinator can summarize it, ask the person, or send more work. Reports are bounded to 4,000 characters.

    If the person talks directly to a worker, the server copies that exchange to the coordinator for awareness, without automatically running it. Approval, error, and stuck states can trigger a report; a person's pause must not become an automatic resume.

    SDK need: event subscribers, report delivery, recovery, and run admission. This adds automatic model runs, not just stored metadata.

  5. The board shows what needs attention

    The server records whether a turn answered or asked a question, a short ask, and whether it is resolved. The UI groups conversations using these fields and execution status.

    A resolution judge can make additional model calls to decide whether anything remains for the person. It uses a configured decision model or the conversation's LLM. OH_RESOLUTION_MODEL=off disables the judge; a confident critic score can still auto-resolve.

    SDK need: derived board metadata and an automatic resolution policy. The judge's input/output is separate from the conversation's main LLM history. This policy can be reviewed separately from project storage.

Sources: sender headers · report delivery and wake rules · board subscriber · judge selection

A coordinator cannot approve for the person. Its messages are marked as coming from another conversation. Guarded delivery refuses a recipient already waiting for approval, paused, errored, or stuck. If the state changes during delivery, the message may be saved without running. Sender labels and run guards serve different purposes; both matter.

Two kinds of shared material

Artifacts

Files to hand over

Reports, images, patches, or other deliverables live in project storage outside Git. People upload them; agents copy an existing workspace file with write_artifact. Other conversations can list and read them.

Up to 100 MiB per artifact. Reads return small text inline or copy the file into the worker's workspace. Downloads are attachments, not executable HTML previews. Upload alone does not put the file into an agent's prompt.

Memory

Facts to carry forward

A project has a MEMORY.md index and named Markdown topics. The index enters project launch context; agents read topics when needed and update them through tools.

Up to 64 KiB per file. Writes carry a base revision; a conflict returns the current file instead of silently overwriting it. The whole memory store is not injected into every turn.

What does the agent actually see?

The saved event stream and the messages sent to the LLM are different views. Projects mostly reuse existing events. Reactions add a new event type; Voice adds transport models.

What changes in the SDK repository?

“SDK” here includes the Python agent SDK, Agent Server, and tools packages. Most new HTTP routes and project storage belong to Agent Server. Canvas and Insider display the board and operate these APIs; they do not own the saved agent loop.

Projects REST API · 20 operations

All paths below start with /api/projects. {p} is a project ID, {c} a conversation ID, and {name} a file name.

GET, POST          /api/projects
GET, PATCH, DELETE /api/projects/{p}

PUT, DELETE        /api/projects/{p}/conversations/{c}
POST               /api/projects/{p}/conversations/{c}/resolve

GET, DELETE        /api/projects/{p}/artifacts/{name}

Project records contain id, name, description, optional coordinator_conversation_id and worker_agent_profile_id, and timestamps. Conversation listings add attention, turn, ask, resolved, and resolve_note alongside execution state and identity.

Memory PUT uses content and base_revision; conflicts return 409 with the current file. DELETE also requires a revision. Project deletion removes project files, artifacts, and memory, but leaves the conversations and their project tags in this snapshot.

Existing message API · sender and guarded-run semantics

POST /api/conversations/{c}/events gains sender_conversation_id and refuse_pending_confirmation on ConversationMessageRequest. These fields are not added to a new conversation's initial_message model.

A conversation sender is saved as conversation:<id hex>, with a text header naming its role. Project senders may address only conversations in the same project. Their run requests are always guarded.

SendMessageResponse adds run and previous_status. Outcomes distinguish started, queued, not_run, and states held for the person: waiting_for_confirmation, paused, error, stuck. HTTP success alone is not a promise that the recipient ran.

Contract: request and response models. This changes an existing public surface, not just /projects.

Experimental settings · defaults and limits 
GET   /api/settings/experimental
PATCH /api/settings/experimental/{key}  {"enabled": true}

The stored feature keys are projects and conversation_reactions, both off by default. Enabling them changes tools on newly created OpenHands conversations, not ACP agents. Disabling them does not remove tools already attached to a running conversation.

HTTP routes check the current switch: Projects returns 404 when off; reactions returns 409. Project data remains stored. These switches are rollout controls, not complete revocation mechanisms. Voice has its own provider configuration and eligibility rules.

Alongside Projects: reactions and Voice

These improve interaction with agents but are separate review decisions. Projects does not need audio to coordinate workers.

Reactions: a small signal that persists

SDK #6609 adds react / unreact, LocalConversation.react(), and POST /api/conversations/{c}/reactions. A reaction acknowledges a message without ending the agent's turn. The Projects snapshot already includes this work; do not count it twice.

The new ReactionEvent is LLM-convertible. The person’s reactions enter the agent's next turn. This is an agent-history decision as well as a UI feature.

Reaction event and tool-execution changes

Fields: target_event_id, emoji, removed, target_text_ending, and target_text_clipped, plus ordinary event identity, time, and source. Six shortcodes are accepted: eyes, +1, white_check_mark, tada, thinking_face, heart.

Clients fold events by target, emoji, and source; the latest wins. Tool execution gains a generic Observation.follow_up_events() hook so the reaction tool can emit the persistent reaction after its observation. Agent-authored reaction events are excluded from the LLM view because the tool call already records that action.

Sources: ReactionEvent · reaction tools and follow-up events.

Voice: talk to a saved agent

SDK #5180 adds a realtime voice connection in front of a saved Insider controller. The voice layer handles speaking and listening. Accepted work goes to the saved OpenHands conversation; that agent uses its normal tools and records the result.

The voice session receives a bounded text snapshot: recent messages, final answers, and condensation summaries, up to 40 blocks / 12,000 characters. It does not receive the whole tool log. Ending the call does not cancel work already accepted by the saved agent.

Voice routes and coupling to review

Prefix: /api/conversations/{c}/voice.

GET    /voice                        availability
POST   /voice/realtime               SDP offer → answer
GET    /voice/realtime/{call_id}     call state / transcripts
DELETE /voice/realtime/{call_id}     end call
POST   /voice/messages              accept a text task

Realtime responses identify the provider (openai or codex), client/server delegation, model, and optional call ID. Call state and VoiceTranscript are transport models, not conversation event types. The provider's send_to_insider and end_voice_call functions are not new tools in the saved agent's tool registry.

The current route explicitly requires a top-level conversation tagged smolpaws=insider with insiderrole absent or set to controller. It includes OpenAI provider support and optional Codex support. Whether that app-specific eligibility and provider lifecycle belong in Agent Server is a separate design question.

Task admission uses a guarded idle-send operation: busy/approval conflicts return 409 and run-capacity failures return 429 without saving the rejected request. The PR also changes direct condensation so it does not run pending tools. These are additional conversation-lifecycle changes, not new voice event types; this source walkthrough does not establish that all handoff races are resolved.

Sources: voice routes · conversation lifecycle.

Decisions a maintainer can review separately

Project resources

Should Agent Server own membership, artifacts, and shared memory? Are the storage, deletion, and revision contracts right?

Coordinator and worker roles

Are prompt presets and editable profiles the right boundary? Is the profile-based child launch compatible with other uses of child conversations?

Automatic orchestration

Should the server deliver reports and wake the coordinator? Are sender identity, recovery, and the person's stop/approval controls sufficient?

Board policy

Should resolution judgments and their extra model calls ship with the project resource, or be an independently selected policy?

Reactions in history

Is converting human reactions into user messages the right semantics? Is the generic follow-up-event hook the right tool-execution extension?

Voice ownership

Should the server broker realtime providers? Should eligibility describe a general saved agent instead of Insider-specific tags?

The first scope discussion can answer these questions without approving every line. Storage, role prompts, automatic runs, reaction history, and voice transport each introduce a different responsibility.
