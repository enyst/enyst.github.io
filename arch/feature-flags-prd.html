01 / Purpose

Test ideas before choosing a new default.

The user needs to know

  • What will change?
  • Where will it change?
  • When will it take effect?
  • How can I undo it or report a problem?

The team needs to learn

Does the feature help the people who choose it? What fails? Should the team improve it, make it a regular option, make it the default, or remove it?

Volunteers do not represent all users. Opt-in feedback alone cannot prove that everyone wants a new default.

Each switch tests one understandable change. Do not put unrelated changes behind one “beta” switch.

03 / Product rules

A switch is a choice, not a permission grant.

Choice and scope

  • Every new experiment starts off.
  • Save only the switches the user changed. Show success only after the server confirms.
  • Show an error and keep the draft if Save fails. If the outcome is unknown, re-read the server state before retrying.
  • In Cloud, save for the signed-in user in the current organization.
  • Locally, save for the active server's settings store. This is not a separate identity for every browser user.
  • Keep choices separate across backends, organizations, and accounts.

Safe operation

  • Keep existing permission checks and confirmation rules.
  • Show unsupported features as unavailable, with a reason.
  • Do not enable a feature while support or settings are still loading.
  • Ignore unknown experiment IDs. Keep stored choices when possible.
  • A deployment owner can disable an experiment. Explain this in the UI.
  • “Turn all off” saves explicit off values for known experiments. It does not undo completed actions.

When does a change apply?

Kind of changeApply itTurning it off
Canvas displayAfter a successful Save.Restore the regular display. Do not delete user data.
Conversation or agent behaviorFor new sessions. Save the resolved configuration with the session.Future sessions use the regular behavior. Existing sessions keep their saved configuration.
Scheduled automationOnly after explicit selection in that automation's configuration.Future runs follow the saved automation choice. A personal Canvas switch must not silently change unattended work.

Each experiment must state its effects and limits. A safety stop may override saved behavior at the next safe boundary. It cannot reverse an action already taken. The feature owner must define that stop before release.

Keep the first release small

Do not add random user assignment, percentage rollouts, a paid flag service, or a general-purpose rules engine. Keep unfinished developer-only work behind existing deployment controls. Keep ordinary, stable preferences in their normal settings pages.

05 / Proposed implementation

One catalog. One saved choice. One check.

1. Describe

A bundled Canvas catalog gives each feature an ID, a plain description, scope, support check, owner, and feedback link.

2. Save

The settings adapter saves a sparse map of user choices. Read it again after Save.

3. Apply

A single resolver checks the choice, implementation support, and deployment policy. The feature calls that resolver.

active = known feature AND saved choice is true AND supported AND allowed

Missing or failed inputs mean off. Capability means “this implementation can do it.” Policy means “this deployment permits it.” The user's choice supplies neither.

Canvas-only pilot: reuse the local settings API

Add experimental_features to Canvas' Settings, APP_PREFERENCE_FIELDS, and preference adapter. Proposed local write:

PATCH /api/settings
{
  "misc_settings_diff": {
    "app_preferences": {
      "experimental_features": {
        "compact_session_list_v1": true
      }
    }
  }
}

Send all changed IDs in one sparse diff, in one atomic Save. The server must accept all of it or none of it. Do not split one Save into per-switch requests. Do not send a whole stale settings object. To turn a feature off, send false. Do not use an empty map to clear a deep-merged map.

The UI-only catalog is shipped with Canvas. Its implementation is available in that build. The local server only persists the preference. A separate policy source is needed if the deployment must prohibit a UI experiment; the preference map is not that source.

Concurrent writes to different IDs must preserve both changes. For the same ID, the last accepted write wins. Refresh on page entry and backend change; re-read authoritative state after Save. Test this with the real persistence path.

Cloud: agree on the contract before enabling the page

Propose the same logical map as a flat experimental_features field through the existing Cloud adapter. The Cloud service must validate known choices, commit all changed IDs atomically, merge only changed IDs, and scope reads and writes to the authenticated user and organization.

Confirm this contract with the Cloud owners. The public adapter does not prove that Cloud accepts or preserves this new field. Until it does, show the experiments as unavailable there; do not report a successful local-only Save.

For locked Cloud builds, allow the Experimental features route in both the settings navigation and the route guard, or provide the page in the Cloud settings shell. Pick one canonical page. Do not duplicate independent switches in both shells.

Runtime experiments: use explicit configuration, not an opaque flag bag

The server owns execution. Resolve an experiment into a typed, supported configuration when a session starts. Persist the result with that session. Validate it at the server boundary for every client.

start a new session
  read the confirmed choice for the active backend
  verify that this backend supports the requested behavior
  build the existing typed session configuration
  create the session and persist that configuration
  run with that saved configuration on resume

Example: a topic-first title experiment can select a reviewed title prompt and pass it through the existing ConversationConfig.prompt. The current pinned schema limits this prompt to 2,000 characters. Check the actual server version and schema; do not assume a pending limit-removal change has shipped. Never overwrite an explicit per-session prompt.

Keep the previous path when the experiment is off. Existing titles do not change. Resume and fork must follow documented configuration rules, not today's global preference. The title study found mixed collection-level results, so it supports a trial, not an automatic default change.

For new execution behavior, add explicit capability and configuration support in the SDK/agent-server first. Update the TypeScript client and Cloud forwarding path as needed. Keep authorization, execution checks, and emergency stops on the server. Generic runtime experiment storage or APIs are outside the first release.

Where the work belongs

  • Canvas: catalog, page, settings types, adapter, resolver, feature UI, translations, tests.
  • SDK / agent-server: only the runtime support a chosen experiment needs; typed APIs, persistence, capability tests.
  • Cloud: account/organization storage, policy, settings page access, runtime forwarding.

Keep separate

  • CLI: its own UI preferences; opt in explicitly to shared runtime features.
  • Automation: saved automation/run configuration; no inheritance from a browser switch.
  • Extensions: reusable skills, plugins, and app packages. They do not own core Canvas flags.
06 / Delivery and acceptance

Prove one full path first.

  1. Choose one reversible UI experiment. Compact session rows are a low-risk candidate. Confirm that real users want to try it. Name a feature owner and a public feedback issue.
  2. Ship the local path. Add the catalog, page, sparse persistence, resolver, and on/off behavior. Document local settings scope. Keep unsupported deployments visibly unavailable.
  3. Add Cloud parity. Land the storage contract, authenticated scoping, policy behavior, and locked-build route change together. Verify local → Cloud → organization switches.
  4. Add one runtime experiment only when needed. Title generation is a candidate. Verify create, resume, fork, and Cloud behavior. Add a reliable support signal before exposing its switch.

Release checks

  • A fresh install behaves exactly as before. Missing preferences and unknown IDs do not enable anything.
  • A saved switch survives reload. Two independent switches remain independent.
  • A rejected Save leaves the active behavior unchanged and keeps the user's draft. A timeout triggers a state check before retry, since the server may have accepted the write.
  • Changing backend, organization, or account cannot reuse another scope's choice.
  • An older or blocked deployment explains why a feature is unavailable.
  • Keyboard and screen-reader users can find the page, change each switch, Save, and read the result.
  • Runtime changes affect only the stated sessions or runs. Direct API calls enforce the same constraints.
  • Opting in never grants permission to publish code, create PRs, spend money, or bypass confirmation.
  • Disabling the experiment restores the regular path without deleting user data.

Feedback and removal

Each experiment needs a named owner, a review date, one main question, and a removal plan. Measure feature use and errors only under the existing analytics consent and Do Not Track rules. The feature must work without analytics. Let users submit feedback without automatically sending their conversation.

At review, choose: improve the experiment, make it a stable setting, make it the default, or remove it. Tell users what changed. Preserve an explicit opt-out where it still has meaning. Stop reading retired IDs before removing their stored data. Follow SDK and REST API deprecation rules if a public field changes; deleting a UI switch does not waive them.

07 / Decisions needed

Approve the product shape, then pick the pilot.

Recommended

Separate switches. Off by default. A dedicated settings page. Existing settings storage. One reversible Canvas experiment first.

Keep apps as a separate path for optional, self-contained tools. Do not delay a small experiment page on a general UI extension framework.

Still to agree

  • Which real feature should be the first pilot?
  • Who owns each experiment and its review date?
  • Should locked Cloud expose the Canvas page or host it in its own settings shell?
  • Does Cloud already offer suitable per-user, per-organization storage and deployment policy?
  • Must local deployments support an operator block in the pilot, or can that follow before runtime experiments?
Alternatives considered
  • One beta switch: smaller initial UI, but users cannot choose one change or report which one helped.
  • Environment variables only: useful for deployment work; hard for ordinary users to discover and change.
  • Apps only: useful for new pages and packaged tools. General composer and core UI customization needs more host APIs.
  • External flag platform now: useful later for managed rollouts. Adds a service and policy surface that this opt-in pilot does not need.
