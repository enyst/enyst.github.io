1What changed, exactly

Three edits, one behavior change. (1) The tool description (the prompt the LLM reads) is reworded. (2) create() attaches a structured FinishTaskOutcomeResponse via set_response_schema(...). (3) FinishAction is unchanged — still just message: str. The structured task_outcome rides on a response schema, not on the action.

The new schema is one field wrapping the outcome model:

class FinishTaskOutcomeResponse(BaseModel):
    task_outcome: TaskOutcome   # status, summary, blockers[], confidence, needs_user_action

set_response_schema merges the schema's fields into the tool's parameter schema (and rejects any name that collides with message or reserved fields). So the model emits message and task_outcome in a single finish call — no second tool, no extra round-trip. tool.py: set_response_schema

5The v0 risk worth an eval

Engel's point on the thread: in v0, some LLMs treated finish as required after every step — they'd call it to ask a question or reply, not only to end. Making finish the carrier of a rich structured schema makes it a more "attractive" tool to call. Worth an eval on a cheaper/weaker model to confirm this reword doesn't nudge premature or over-eager finish calls back. The mitigation in-PR is that the schema is additive and message stays the primary field, but the prompt no longer lists "follow-up questions" as a finish use — which is arguably good (discourages finish-to-ask) but changes behavior.
